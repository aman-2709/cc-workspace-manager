# CC Workspace Manager — Requirements (v0.1)

Status: **Approved for implementation** · Single source of truth · Supersedes all earlier specifications and amendments (see Appendix A)

> **Install once. Automatically discover projects. Track development activity. Know where you left off. Resume work effortlessly.**

**Fundamental guarantee.** CC Workspace Manager reads your projects. It does not modify them, push them, or upload their data anywhere. It does not intentionally execute their contents: it neutralizes repository-defined Git helpers, blocks every Git transport in a way repository configuration cannot override (so a lazy fetch in a partial clone cannot run a remote helper), and sandboxes itself and its Git subprocesses where the kernel supports it. The Git flags are not the only line of defense and not a sandbox (§6). SECURITY.md lists the residual limits. Never claim a guarantee beyond what is enforced and tested.

## 2. Principles and non-goals

Principles, in priority order: correctness → security → resource efficiency → maintainability → ease of installation → feature count.

Non-goals for v0.1:
- **Zero external network communication.** The only network traffic is loopback HTTP/WebSocket to the browser and the Unix-socket CLI channel. Prohibited: telemetry, analytics, crash reporting, external AI APIs, cloud sync, update checks, uploading any project, session or system information, external fonts/scripts/images/CDNs, and network access by Git subprocesses. External programs the user runs themselves (e.g. Claude Code via a copied resume command) are outside this guarantee; document that.
- **Strictly read-only monitoring.** ccwm never creates, modifies, deletes, renames or changes permissions of any monitored project file, Git repository (including `.git/index` and `.git/config`) or Claude Code session file. It never creates CLAUDE.md files or writes metadata into projects. During normal operation, only ccwm's own config/data/state/runtime directories are writable. `ccwm service install|uninstall` and the install scripts may modify only their documented installation locations.
- No automatic execution of anything extracted from projects or sessions.
- No remote or LAN access. Binding is loopback only, and non-loopback binding is not supported.
- No generic "AI assistant provider" abstraction. Keep the Claude Code integration in its own module and introduce an abstraction only when a second provider is actually built.
- No macOS/Windows support claims.

## 3. Platform and stack

- **Platform:** Linux x86_64. Ubuntu is the primary test target. Only report distributions and environments that were actually tested.
- **Language:** stable Rust. Declare an MSRV in `Cargo.toml`. Commit `Cargo.lock`.
- **Crates:** Axum (HTTP + WebSockets), Tokio, notify, rusqlite with `bundled` SQLite, serde / serde_json, clap, tracing (+ tracing-subscriber, journald-friendly output), a TOML crate for config, and `landlock` for sandboxing (§11.5). Choose walkdir or ignore for traversal (the `ignore` crate is preferred because it evaluates `.gitignore`). Before adding any other dependency, justify it in ARCHITECTURE.md.
- **Frontend:** HTML, CSS and vanilla JavaScript, embedded in the binary. No CDNs, external fonts, frameworks or build step that needs Node.
- **External runtime dependencies:** `git` (optional; Git features degrade gracefully without it) and `claude` (optional; used only to verify resume syntax). Document both.

## 4. Project discovery (v0.1)

### 4.1 Roots and scope
- The default discovery root is the home directory of the non-root user running the service, resolved by platform mechanisms (`$HOME` if it is an absolute path to a directory owned by that user, which is what systemd and login shells provide and what the synthetic test environment of §19 overrides; otherwise the passwd entry of the effective UID). Never hardcode `~/dev` or a username. Refuse to run as root.
- Users can add, remove and narrow roots (including roots outside home that they explicitly authorize) and add exclusion patterns. Root, exclusion, depth and file-system changes are saved and take effect at the next start (§9; approved 2026-11-24, O1). This is permanent: Landlock cannot widen the read set of a running process, so there is no in-process reconfiguration.
- Hard safety boundaries that explicit roots can never override: `/proc`, `/sys`, `/dev`, `/run`, the ccwm data, config, state and runtime directories, and any path not readable by the user.
- `same_file_system = true` by default. Symlinked directories are not followed by default. Max traversal depth defaults to 10 (configurable).
- Paths that are not valid UTF-8 are skipped and counted (`non_utf8` in the discovery status); they are never registered.
- Discovery reads **directory entries and metadata only**. File contents are read only for CLAUDE.md markers (bounded size; a content hash is kept to recognise moved projects, §4.5), Claude session files, and `.gitignore` files and `.git/info/exclude` (bounded per file, per project and across projects, §5.2) for the in-process ignore evaluation of §5.2.

### 4.2 Default exclusions (configurable)
Skip hidden directories by default (`.*`, which covers `.git`, `.cache`, `.local`, `.config`, `.ssh`, `.npm`, `.cargo`, `.rustup`, `.claude`, `.venv`, browser profiles, trash). Also skip `node_modules`, `target`, `build`, `_build`, `dist`, `venv`, `__pycache__`, `~/snap`, cloud-sync and FUSE mounts (detected via mount type where possible, e.g. `fuse.*`), VM and container image directories (e.g. `~/VirtualBox VMs`, `~/.local/share/containers` already hidden), and generated artifact and log directories. Prune excluded directories **before** descending. `~/.claude` is read only by the session integration (§7).

### 4.3 What qualifies as a project
Sessions are the **primary** discovery source; the marker scan is secondary (§4.5). A directory is a project candidate if **either** of these holds (both enabled by default):
1. **Session:** the first recorded working directory (cwd) of a Claude Code session exists, lies within the allowed roots, and is not excluded; it resolves to a project root as in §4.4.
2. **Marker:** it contains a file named exactly `CLAUDE.md` (case-sensitive). A `CLAUDE.md` that is a symlink counts as a marker (a common `AGENTS.md` pattern). Its target is read only if it resolves to a regular file inside the same project directory.

Never a project: the home directory itself, `~/.claude`, anything under a hard safety boundary, and paths in the ignore list.

### 4.4 Resolving project roots
- **Session cwd → project root:** walk upward from the recorded cwd (canonicalized) to the nearest directory that is a Git work-tree root (a `.git` entry) or has a `CLAUDE.md`, without crossing the discovery-root boundary and never reaching the home directory (a dotfiles repository at home is not a project's repository). Then the nested rule below applies, against the marker directories on disk as well as the registered projects (so the outcome does not depend on what is registered yet: a session in `monorepo/services/api` — a `CLAUDE.md` without its own Git work tree inside a marker project — belongs to `monorepo` on the first launch too).
- **Session-only candidates** (maintainer decision, M3.1; M3 security review M4): if no Git work-tree root and no `CLAUDE.md` is found, the cwd itself is a *session-only* candidate. It **never acts as the outer project** of the nested rule (in session resolution and in marker scans), and it is registered only if **no marker directory, Git work tree or registered project lies below it** (a bounded descriptor-based look below it, following discovery's exclusions, depth and file-system rules; a tree of more than 2,000 directories counts as having one). Otherwise the session is unassigned with the reason `container` (e.g. a session started in `~/dev`, which must not swallow the projects below it).
- **Unassigned sessions** (never projects; counted by reason in the discovery status): no usable cwd (`no_cwd`), a cwd that no longer exists or is not a directory (`nonexistent`), the home directory or an ancestor of it (`home`), a temporary directory — `/tmp`, `/var/tmp`, `/dev/shm`, `$TMPDIR` — unless the cwd is inside the home directory (`temporary`), outside every discovery root (`outside_roots`), below an excluded directory or a hard boundary, on another file system than its root (with `same_file_system`) or deeper than `max_depth` below its root (`excluded`), a session-only container (`container`). Unassigned sessions are resolved again at every reconciliation (a cwd may appear later; projects may appear below a container).
- **Store both** the resolved project root (for grouping) and the original session cwd (the **first** recorded cwd, for resume, §8).
- **Nested candidates:** if candidate B lies inside candidate A, B is a separate project only if B is a Git work-tree root different from A's. Otherwise B's `CLAUDE.md` is treated as a nested instruction file belonging to A. Ordinary Git subdirectories never become projects. A is a marker directory or a registered project with a Git work tree or a `CLAUDE.md` at its root; a session-only project is never A.
- File activity inside a nested project is attributed **only** to that nested project, never to its parent.
- Canonicalize all paths and deduplicate on the canonical path. Record every discovery source per project (`marker`, `session`, or both) and show it in the UI.

### 4.5 Lifecycle
- **First launch:** the server starts immediately. Discovery runs in the background and publishes projects progressively over WebSocket: sessions first, then a **full marker scan** of every root (to catch projects whose transcripts Claude Code already pruned). **Later launches:** cached projects are shown immediately and reconciled in the background.
- **Marker-scan scope after the first full scan:** reconciliations scan for markers only below the **development roots**: the parent directories of present session-discovered projects that lie within a discovery root, walked 3 levels deep (a development root that is a configured root or the home directory: 1 level). The setting "Scan entire home" (`discovery.full_scan`) restores a full scan of every root at every reconciliation. The discovery status reports the scope and the development roots.
- **Persistence:** a project, once discovered, persists while its directory exists, even after its marker or its session files are deleted. It becomes **missing** when its directory is gone (and its root is available); a missing project whose directory returns is revived with its id.
- **New projects:** a new `CLAUDE.md` in a watched directory, or a new session (the session directories are watched, §7.2), registers a project, enriches it and publishes it live, without a restart or page reload. In unwatched locations, the project appears at the next reconciliation (for markers: if inside the scan scope above).
- **Moves and renames:** use paired inotify rename events when available. Otherwise treat a missing project plus a new project with the same Git HEAD commit and remote (or the same CLAUDE.md content hash for non-Git projects) as a move, and keep the project's ID. If no match is found, mark the old project **missing** (shown in a "Missing" filter) and purge it after the retention period (default 30 days, configurable). Never silently delete projects.
- **Ignore:** users can permanently ignore a project. The ignore is stored by canonical path, and source files are untouched. Ignored projects are hidden and can be un-ignored in Settings.
- **Forget** (maintainer request, M3.1): a **missing** project can be forgotten from the UI before its retention ends. It is removed from ccwm's database only (its sessions become unassigned and are resolved again); nothing on disk is touched. A present project cannot be forgotten (ignore it instead).
- **Reconciliation:** a low-priority scan of the roots (default every 10 minutes, configurable). It must not overlap with a running scan, must use bounded concurrency, and must back off on errors. Manual refresh triggers a coalesced reconciliation.
- **Errors:** permission errors, vanished paths and inaccessible mounts are counted and skipped. Discovery never aborts because part of the tree fails. Error reports avoid leaking full sensitive paths unnecessarily.
- **Discovery status** exposes: phase, progress, projects found, skipped/error counts, last successful scan and next scheduled reconciliation.

## 5. Filesystem monitoring and activity (v0.1)

### 5.1 Watches
- **Never** use notify's recursive mode on Linux. Walk eligible trees explicitly, apply exclusions first, and register **non-recursive** watches on eligible directories only.
- Watch targets: project trees (excluding excluded and gitignored directories) and the parent directories of known projects (to detect new sibling projects). Never watch the whole home directory recursively.
- Add watches dynamically for newly created eligible directories, and remove obsolete ones.
- Use exactly **one** notify watcher (one inotify instance) for the whole daemon, because `max_user_instances` is a small shared pool. If the instance cannot be created, start with every project in polled mode and report it (banner, `ccwm doctor`).
- **Watch budget:** default 25% of `/proc/sys/fs/inotify/max_user_watches` (no fixed ceiling; 8192 if the limit cannot be read), configurable. The inotify pool is shared with IDEs and other tools. Allocation is **breadth first**: every project's root directory, then the parents of project roots (sibling detection), then every project's `.git` and top-level directories, then deeper directories of the most recently active projects first. Gitignored directories (including rules from a repository root above the project) are never watched.
- **Degraded mode:** when the budget or the kernel limit is reached, or on queue overflow (`IN_Q_OVERFLOW`), never change kernel limits automatically, and cover what has no watch in reconciliation (mtime checks): a project whose root is watched but not all of its tree is *partly watched* and only its unwatched subtrees are polled; a project without a root watch (or without an inotify instance) is *polled* as a whole. `ccwm status` reports partly watched and polled projects separately. **Partly watched projects with nothing polled are normal operation, not degraded.** "DEGRADED" and the degraded-monitoring banner (one line, details behind a toggle) are reserved for real failures: no inotify instance, a queue overflow being recovered, or projects without any watch (polled). Exposing `ccwm doctor` guidance is fine.
- Debounce and coalesce events per project (default 2 s). Bounded queues everywhere.
- Never generate activity from ccwm's own writes. The data, config and state directories are excluded unconditionally, under their configured and their canonical paths (a symlinked XDG directory that resolves into a project must not make ccwm watch its own database); the home directory is used in its canonical form by discovery, the tracker, the watcher and Git alike.

### 5.2 Meaningful activity
- A modification is *meaningful* if the file is not excluded (§4.2), not inside a nested project (§4.4), and, for Git projects, not gitignored and not under `.git/`. Hidden *files* count (§4.2 excludes hidden directories). Creating or removing a directory counts as activity but does not change the "latest modified file". Changes under `.git/` invalidate the Git cache (§6) instead. Gitignore evaluation is done in-process (the `ignore` crate's matcher), never by running `git check-ignore`; it approximates Git's own behavior and the differences are documented. **Ignore files are bounded** (compiled rules stay in memory, and a repository chooses how many it has): at most 256 KiB per `.gitignore` / `.git/info/exclude`, at most 1 MiB and 5,000 rules for all ignore files of one project, and at most 20,000 rules for all projects together (a directory tree also chooses how many projects it holds; v0.1.1). A file over a limit is skipped whole (never read in part), counted, and reported in the monitoring status and `ccwm status`; its rules do not apply (except at the scans of a project that only the limit across projects holds back, below). **The limit across projects goes to the most recently active projects** (the order of the watch budget, §5.1; decided by the maintainer, 2026-11-26), not to whichever project was walked first: by last recorded activity, most recent first, projects without a recorded time last, the path deciding between equals. Each project keeps all the rules it wants while they fit in what is left; the first one that does not fit completely keeps the files that still fit; the ones after it keep none. The outcome depends on the projects alone, not on the order or the timing of their walks; it is re-established after every walk and every change of the project list (a change of a session file included), at the latest at every scan, a project giving rules up before another takes them, so the total stays within the limit. One full walk of a project runs at a time. A project that is no longer monitored frees its share. **A walk of part of a project's tree** — a directory created or moved in at runtime, an unwatched subtree polled at a scan — **holds no more rules than the project does**: it compiles no ignore file beyond them, however many such walks run at once; an ignore file it cannot take that way (new, or changed) has the project walked whole, which reads it within the limits above (v0.1.1 review M1, decided by the maintainer; before, each such walk could compile a project's worth, and 24 directories moved in together took the daemon past 2 GiB). **Compiled rules are cached** (decided by the maintainer, 2026-11-26): the rules of an ignore file are compiled again only when the file changed — its device, inode, size, modification time or change time — and a project that is no longer monitored takes its cached rules with it. The change time (`st_ctime`) is part of it because nothing can set it back: a file rewritten in place to the same size with its modification time restored is still seen as changed. A file whose modification or change time is less than 2 s before the walk reads it is compiled but not kept for reuse (Git's rule for its index, v0.1.1 review I5): a rewrite to the same size within one step of the file system's clock (from nanoseconds up to 1 s on ext4 with small inodes) is then seen as well. What is not noticed: on a file system without a change time of its own (FAT), a rewrite to the same size with its modification time restored; the cache is not keyed by content. The repository whose rules apply is the nearest `.git` at or above the project root, searched no higher than the project's discovery root and below home, and only if that `.git` is owned by the user (as Git itself requires).
- Each project tracks: latest meaningful modification timestamp, latest modified file (relative path), and a bounded list of recent file events (default last 200 per project; create/modify/delete/rename; retention configurable). Timestamps have one-second resolution and never move backwards; within the same second an observed timestamp is never replaced by an inferred one.
- **Inferred vs observed:** the initial timestamp, computed by a bounded walk at first discovery, is labeled `inferred`. Timestamps from live events are labeled `observed`. The UI shows which it is. Unknown timestamps stay unknown and are never invented. A project that lacks ignore rules because of the limit across projects is **scanned with all of them** (v0.1.1 review M2, decided by the maintainer; this replaces the earlier rule that such a scan never moves a known time, which left a polled project's activity stale for good): its inferred time comes from a walk with the rules its own limits allow, compiled for that walk alone and dropped when it ends, one such walk at a time — beyond the limit across projects there is never more than one project's worth of rules — and a partly watched project that lacks rules is walked whole. So its real activity is seen (scans are a polled project's only source), a file its rules ignore never counts at a scan, and giving rules up never makes a project look active. The watcher judges events with the rules a project keeps: in a project that lacks some, a change to a file the missing rules would ignore is recorded as activity like any other (the watcher cannot tell them apart, v0.1.1 review L6), and activity, real or not, moves the project up in the order and can bring its rules back. `ccwm status` names the projects whose ignore rules are limited.

### 5.3 Activity classification
Based on local calendar days since the last meaningful modification (system time zone):

| Status | Calendar days ago |
|---|---|
| Today | 0 |
| Recent | 1–6 |
| Inactive | 7–29 |
| Dormant | ≥ 30 |
| Unknown | no reliable timestamp |

The thresholds are configurable. The **"Modified this week"** statistic = Today + Recent (days 0–6). This is intentional; keep it consistent with the buckets. The relative time shown in the UI ("N days ago") uses the same calendar-day calculation as the bucket (never elapsed 24-hour periods). Recent activity must never be presented as "a Claude session is running".

### 5.4 Sorting
- Default: latest meaningful file modification, newest first. Unknown sorts last. Ties are broken by name.
- Other sorts in v0.1: latest Claude session, latest Git commit, name.
- Git commit and session timestamps are shown separately and never drive the default sort.

## 6. Git integration (v0.1)

- A **single centralized module** runs all Git commands. Nothing else spawns `git`.
- **Allowlisted invocations only:** `--version`, `rev-parse` (top-level, git-dir, HEAD), `status --porcelain=v2 --branch --ignore-submodules=all -z -- .` (branch, upstream, ahead/behind against local remote-tracking refs, staged/modified/untracked; limited to the project directory), `log -1 --no-show-signature --no-notes` with a fixed `--format` (verifying a signature would run `gpg.program`, which repository config can choose), `config --get-regexp` for filter drivers (below) and, after a failed `status`, for promisor remotes (partial clones, below), and `config --get` for `remote.origin.url` (or the URL of the upstream remote, found with `config --get branch.<branch>.remote`). Any `diff` that is ever added must use `--no-ext-diff --no-textconv`.
- **Always pass:** `--no-pager --no-optional-locks -c core.fsmonitor=false -c core.untrackedCache=false -c core.hooksPath=/dev/null -c protocol.allow=never -c protocol.ext.allow=never -c protocol.ssh.allow=never -c protocol.file.allow=never -c protocol.git.allow=never -c protocol.http.allow=never -c protocol.https.allow=never`. The generic `protocol.allow=never` alone is not enough: a per-protocol `protocol.<name>.allow` in the repository's config outranks it, while the per-protocol values given with `-c` outrank the repository's.
- A repository whose top level is the home directory (e.g. a dotfiles repository) is not the repository of a project below it: such projects are reported as not Git.
- **Environment:** start from an empty environment. Set only `PATH`, `HOME`, `LC_ALL=C`, `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_OPTIONAL_LOCKS=0`, `GIT_ALLOW_PROTOCOL=` (empty: no transport at all, remote helpers included; an environment variable overrides any configuration) and `GIT_NO_LAZY_FETCH=1`. Pass arguments as an argument array with no shell. Never pass untrusted strings as options (use `--` where applicable).
- **Partial clones (lazy fetch):** in a promisor partial clone, `status` and `log` fetch missing objects on their own, through the repository's transport (`ext::` commands, `remote.<name>.uploadpack`, `core.sshCommand`). Every transport is therefore blocked three ways that repository configuration cannot override: `GIT_ALLOW_PROTOCOL=` (empty), the per-protocol `-c` denies above, and `GIT_NO_LAZY_FETCH=1` (honored by Git 2.45.0 and by builds carrying the CVE-2024-32465 fix, e.g. Ubuntu `1:2.43.0-1ubuntu7.1` and later; older Git ignores it and the first two still apply). Partial clones are not refused: when `status` fails in a repository with a promisor remote (`extensions.partialClone` or `remote.<name>.promisor`, read with `config --get-regexp`), the project shows the degraded state "Git status unavailable (partial clone)"; the branch and remote URL are still read.
- Timeout of 5 s per command (kill the process group on timeout). Global concurrency limit of 4. Results are cached per project and invalidated by relevant file events (`.git/HEAD`, refs, index) or by reconciliation.
- Handle: no Git installed, non-Git projects, detached HEAD, worktrees, nested repositories, and Git refusing the repo because of `safe.directory` / dubious ownership. Report this as a status and never override it.
- Sanitize remote URLs: strip userinfo and credentials before storing or displaying them, including a password in the scp-like form (`user:password@host:path`) and a password with an unescaped `/`; when it is unclear whether the text before an `@` is a password, drop it.
- **Filter drivers and attributes:** `git status` runs clean/process filter drivers when it re-hashes stat-dirty files, and with `--no-optional-locks` that happens on every call. Reading config never executes anything. Every `status` invocation therefore (a) passes `--attr-source=4b825dc642cb6eb9a060e54bf8d69288fbee4904` (the empty tree, a built-in object, so nothing is written) so `.gitattributes` in the worktree is not consulted, and (b) first enumerates drivers with `git config --get-regexp '^filter\..*\.(clean|smudge|process)$'` (includes and `includeIf` are resolved) and passes no-op `-c filter.<name>.clean= -c filter.<name>.smudge= -c filter.<name>.process= -c filter.<name>.required=false` for **every** driver in **every** scope (system, global, local, worktree, command line), because `.git/info/attributes` can select a driver even when (a) is in effect. Both are required: each alone leaves a verified bypass. The override must name the driver **byte for byte**: a name that is not valid UTF-8, is empty, or contains `=` (Git splits `-c` at the first `=`) or a control character cannot be passed back as `-c filter.<name>.<var>=` exactly, and such a driver cannot be neutralized: worktree `status` is then **not run** for that repository (state "status disabled: unsafe filter configuration"; fail closed). **When a name cannot be represented exactly, refuse; never approximate**: a lossy conversion builds the override for another name and leaves the real driver active (v0.1.0 review H1). Document the consequence: files whose status depends on attributes or filters (git-lfs, `text`/`eol` normalization) can be reported differently from the user's own `git status`.
- **Minimum Git version:** `--attr-source` was introduced in Git 2.41.0 (Git release notes). The hardened `status` has been verified only on Git 2.43.0 and ccwm reports the versions it was tested on. With an older Git, worktree `status` is **disabled by default** and the project shows the state "status disabled: git too old to harden"; a documented opt-in setting (`git.allow_unhardened_status`, default `false`) re-enables it. `rev-parse`, `log -1` and `config --get` stay available. `git status` runs no hooks; `core.hooksPath` is still overridden.
- Investigate every other repository-controlled configuration that can trigger command execution during the allowlisted commands (clean/process filters, fsmonitor, external diff/textconv, pager, credential and ssh helpers, transports reached by a lazy fetch, includes), and document the findings in SECURITY.md. The flags are mitigations, **not a sandbox**, and they are not the only line of defense (Landlock, §11.5, is the other); say so.
- Git subprocesses inherit the daemon's Landlock sandbox (§11.5): read-only filesystem and no outbound network where the kernel supports it.
- **Never** fetch, pull, push, commit, checkout, gc or write to monitored repositories.

## 7. Claude Code session integration (v0.1)

### 7.1 Source and schema
- Session root: the `CLAUDE_CONFIG_DIR` environment variable if set, else `~/.claude`. Configurable. Session files are typically `projects/<encoded-dir>/<session-id>.jsonl`. **Verify the actual layout and schema on this machine before implementing**, and record the findings in ARCHITECTURE.md.
- Never derive project paths by decoding directory names. Use the `cwd` recorded in the session records.
- Maintain a **versioned corpus of synthetic fixture files** (`tests/fixtures/sessions/<claude-code-version>/…`) that reproduce the verified schema: real record shapes, subagent/sidechain records, summaries, tool-result "user" records, malformed lines and truncated files. **Never commit real session records, even redacted ones.**
- Schema verification follows the development-time privacy rules (§19).
- Parse unknown record types and unknown fields without failing (skip them and count them).
- **Allowlist parsing** (maintainer decision, M3): only the fields ccwm needs are read — `type`, `sessionId`, `uuid`, `timestamp`, `cwd`, `gitBranch`, `isMeta`, `isSidechain`, `isCompactSummary`, `promptSource`, `turnOrigin`, `message.role`, the `message.content` text of candidate prompts (on demand only, deserialized only after the record's flags passed the genuine-prompt checks of §7.3), `aiTitle`, the `continued-in` / `derived-from` links, `version` and `entrypoint`. ccwm never reads or stores `api-request-blob` content, `toolUseResult`, `wireToolInputs`, attachment bodies, `serverClassifierContext`, `queue-operation` content, or the account/organization UUIDs of `session-owner` / `bridge-session` records (the JSON parser skips them without materializing them).
- Only top-level `projects/<encoded-dir>/<session-id>.jsonl` files are sessions, with a **lower-case** UUID stem (Claude Code writes lower case; other spellings are not sessions, and ids are never case-folded). One file per session id: when the same id appears in several directories (e.g. a session file copied after moving a project), the file already indexed wins, else the first by path; the others are counted as duplicates (M3.1, review L4).
- Only these top-level files are read as sessions. Files under `<session-id>/subagents/` and everything else in the tree are ignored in v0.1 (counted as skipped) and the limitation is documented. Session files up to ~80 MB are expected (the largest seen was 76 MB): incremental parsing and bounded tail/head reads keep the cost proportional to what is new or shown.

### 7.2 Incremental parsing
- Keep a checkpoint per file: device, inode, size, byte offset of the last complete line, and mtime.
- On append, parse from the offset. Never advance past an incomplete trailing line. If the inode changed or the size shrank, reparse from 0.
- Cap the maximum line size (default 8 MiB). Skip oversized lines and count them.
- Watch the session directories non-recursively for changes, with debouncing.
- **Listing limit:** one listing of the session directory holds at most 100,000 session files; the rest is counted as skipped. A session is removed from the index as gone only on the basis of a complete listing of its folder: when the limit cut a listing off, no session of the folders it cut off is removed (v0.1.1, v0.1.0 review I8); the folders it listed completely still lose the sessions whose files are gone (v0.1.1 review I2). That state is logged when it begins and when it ends, not at every ingest, and shown in `ccwm status`.
- **Early stop** (maintainer request, M3.1): a session not assigned to a project is read only up to its first recorded cwd when that cwd can never name a project while the daemon runs (`no_cwd`, `home`, `temporary`, `outside_roots`, `excluded`); its checkpoint is marked partial and later appends are not read. If the cwd may name a project later (e.g. other roots after a restart), the file is parsed again from byte 0.
- **Parser version (M4):** `PARSER_VERSION` (in `claude::parse`) is bumped whenever a parsing, cleaning or session-file rule changes what is stored for the same file. When the database is opened by a build whose version differs from `meta.session_parser_version` (absent = M3), the derived session index is cleared in the same transaction that records the new version (projects stay), so the next ingest parses every file from byte 0 and no row keeps a value computed by older rules. No schema migration is involved.
- There is no per-record deduplication. Sessions store idempotent per-session aggregates (minimum/maximum timestamps, last-wins title) and the byte-offset checkpoint prevents re-reading, so restarts never double-count.

### 7.3 Extracted data (only what v0.1 needs)
**Stored metadata** per session: session ID, file path, recorded cwd(s) (first and last seen, in file order), start time (the **minimum** timestamp over conversational records, i.e. `user`, `assistant`, `attachment` and `system` records), last activity time (the **maximum**; timestamps are not ordered within a file, so neither the first nor the last line is used), whether it is a subagent/sidechain session (always false for ingested files in v0.1), the Git branch, Claude Code version and entrypoint last recorded, the `continued-in` target and `derived-from` sources (validated UUIDs), and the title.
- **Session title** (maintainer decision): the **latest `ai-title` record** (file order), redacted, at most 300 characters, labeled "AI title (recorded by Claude Code)". Without one, the card says "Untitled session" and the detail panel shows the first genuine prompt, labeled "first prompt", read on demand.

**Prompt text is not stored by default.**
- The **last genuine user prompt** (and the first-prompt fallback) are read **on demand** when the detail panel is opened. Use a bounded tail read (or head read for the first prompt) of the original session file, at most 4 MiB, and truncate to 2,000 characters. Redact the result and don't persist it.
- *Genuine user prompt* (maintainer decision, M3): Claude Code also writes tool results and meta/command records as `user`-type records. A genuine prompt is a `user` record with `message.role = "user"`, not `isMeta`, not `isSidechain`, not `isCompactSummary`, without `toolUseResult` and without `tool_result` content, whose text does not begin with a known synthetic tag, and whose `promptSource` is `typed`, `queued` or `suggestion_accepted` (`sdk` and `system` are never genuine; the session itself still counts; any other value is not genuine). Records **without** `promptSource` (older versions) pass the same checks plus `turnOrigin` not `task_notification`. The known synthetic tags are the §19 script's table **except `<pasted_content>`**, which the schema output shows at the start of a `queued`, human-origin prompt (text the user pasted). Text is the string content or the joined `text` blocks (images are skipped). The last prompt is taken from `user` records, **never** from `last-prompt` records (which are truncated to about 200 characters).
- Cards show the recorded title, or "Untitled session". The truncated **first** genuine user prompt, explicitly labeled "first prompt", appears only in the detail panel, on demand.
- Setting: "Store prompt text" (**opt-in, default off**). When on, the last prompt is cached in SQLite (redacted) for faster display. Turning it off deletes the cached text, and no prompt read still in flight can store text afterwards (the database writer itself checks the setting). Deleted session data does not linger in the database files: deleted content is overwritten (`secure_delete`) and the write-ahead log is checkpointed and truncated after the deletion (M3.1, review M2/L6). A truncation that a reader still using the log prevents is logged and tried again after each later write until it succeeds (v0.1.1, v0.1.0 review I7); the retries do not wait for the reader (only the attempt after the deletion does), the warning is logged once and its payment once, and the first write after a start truncates whatever an earlier run left (v0.1.1 review L3).
- Never store full transcripts, assistant responses, or tool inputs or outputs in v0.1.
- Apply best-effort secret redaction to **everything displayed or stored** from sessions, titles included: PEM and PGP private key blocks, common token formats such as `ghp_`, `github_pat_`, `glpat-`, `npm_`, `AIza…`, `sk-`, `sk_live_`/`sk_test_`/`rk_…`, AWS access keys, `Bearer …`, HTTP Basic credentials, and assignments whose key **ends** in a secret-like word (`password=`, `DB_PASSWORD=`, `aws_secret_access_key = `, `client_secret:`, JSON/YAML-quoted keys such as `"password": "…"`) (M3.1, review M3). Document that redaction is not guaranteed to find every secret. **Exemption:** recorded cwds are paths, not text; they are not redacted (a redacted cwd would break the resume command) and are hidden in privacy mode.
- Stored session strings are bounded: a cwd longer than 4,096 bytes is ignored like an absent one; the Git branch, version and entrypoint are stored without control characters and cut to 256 characters (M3.1, review L3).
- "Clear session index" in Settings deletes ccwm's derived session data only. It never touches the original session files.
- Session duration is shown only when it can be computed reliably from recorded timestamps.
- Never fabricate titles, summaries, progress or pending tasks. Show explicit "not recorded" states.
- Session text is untrusted data. It is never interpreted as instructions and never rendered as HTML.

## 8. Resume commands (v0.1)

- Command form: `cd -- '<recorded-session-cwd>' && claude --resume <session-id>`
- The cwd is the session's **first recorded cwd** (a session can change directory later; the first cwd matches the directory Claude Code stores the session under), not the last cwd and not the resolved project root.
- **Continuations** (maintainer decision, M3): if the session was continued in another session (`continued-in` link), the command resumes the **latest recorded continuation** (links followed while the target is in the index; cycle-safe, at most 16 hops), with that session's first recorded cwd. A continuation that is not in the index is not followed: the session itself is offered with a warning. A link is followed **only to a session assigned to the same project** (M3.1, review L5); otherwise the session itself is offered with the warning `continuation_other_project` or `continuation_unassigned` and the target's first cwd is shown.
- Session IDs must pass strict UUID validation, or no command is generated.
- Paths are shell-escaped with POSIX single quotes (each `'` becomes `'\''`). Add a unit test with adversarial paths (spaces, quotes, `$()`, backticks, leading `-`).
- **Terminal-unsafe cwds** (maintainer decision, M3.1; M3 security review M1): the command is pasted into a terminal, whose line editor acts on control characters before the shell parses anything. If the recorded cwd contains any C0 control character (including `\t`, `\n`, `\r`, `ESC`), DEL, a C1 control character or a Unicode bidi/format character (`U+202A–U+202E`, `U+2066–U+2069`, `U+200E/F`), **no command** is generated; the warning `cwd_unsafe_characters` is shown and the path is displayed escaped (e.g. `\x15`). Tests: no command for a newline, `\r`, `\x15`, `ESC[201~` and `U+202E`; a pseudo-terminal regression test pastes generated commands into an interactive `bash` (with and without bracketed paste) and checks that nothing runs, with a control run proving the harness detects execution.
- **CLI verification:** at startup (and at each reconciliation, only if the binary changed) and in `ccwm doctor`, locate `claude` on `PATH` and run `claude --version` and `claude --help` with a 5 s timeout, inside the daemon's sandbox. Confirm `--resume` is supported and cache the result keyed by binary path, size and mtime. Never run it per request. The result is in `/service/status` and `ccwm status`.
- If `claude` is missing or unverified, still show the command with a warning. If the recorded cwd no longer exists, show a warning.
- The UI offers **copy only**. ccwm never executes resume commands or anything else taken from sessions or projects.

## 11. Authentication and security (v0.1)

### 11.1 Threat model (also documented in SECURITY.md)
- **In scope:** other local Linux users; malicious websites (CSRF, cross-origin reads, DNS rebinding); other localhost services, including ones listening on other ports; malicious project files, CLAUDE.md content, session content and Git configuration.
- In scope also: another local user binding the ccwm port while the daemon is down, to impersonate it.
- **Out of scope:** malicious processes running as the same Linux user (they can read the data directly), a compromised OS or kernel, and root or privileged attackers.
- Claim no protection beyond this model.

### 11.2 Credentials
- **CLI ↔ daemon channel:** a **Unix domain socket** at `$XDG_RUNTIME_DIR/ccwm/ccwm.sock` (directory `0700`, socket `0600`). The daemon authenticates every connection with `SO_PEERCRED`: the peer UID must equal the daemon's UID. The CLI verifies the daemon the same way (peer UID equals its own) before sending anything. The protocol is newline-delimited JSON (one request object and one response object per connection) dispatched into the **same service layer** the HTTP handlers use; no HTTP client or server is involved, and HTTP client crates are banned (§11.5). If `XDG_RUNTIME_DIR` is unset, the runtime directory falls back to `$XDG_STATE_HOME/ccwm/run/`. In either case the directory must be owned by the user with mode `0700` (verified by the daemon and by the CLI) and the socket path must fit the 108-byte `sun_path` limit, otherwise startup fails with a clear message. **The CLI never sends credentials over TCP**, so an impostor on the TCP port receives nothing. There is no CLI token file.
- **Bootstrap token:** `ccwm open` asks the daemon over the Unix socket for a random single-use bootstrap token valid for 30 s, along with the TCP port the daemon actually bound. Only then does it open `http://127.0.0.1:<port>/#bt=<token>` (or print the URL with `--print` or when no display is available). The single canonical browser origin is `http://127.0.0.1:<port>`; `localhost` is a different origin and would split `localStorage`.
- The page reads the fragment, **removes it immediately** with `history.replaceState`, and exchanges it (`POST /api/v1/auth/exchange`, which requires a valid, unexpired, unused bootstrap token) for a **session token**. The session token is 32 random bytes, stored in `localStorage`, valid for 30 days on a sliding basis, and rotated at least every 24 h via `POST /api/v1/auth/rotate`, which issues a new token and keeps the previous one valid for 60 s (so concurrent tabs don't race).
- **Rotation is enforced:** once a session token's rotation is overdue (more than 24 h + 60 s since the session last rotated), the daemon accepts it **only** on `POST /api/v1/auth/rotate`.
- **Live sessions are bounded:** at most 10 live browser sessions; creating an 11th revokes the least recently used one. Expired sessions are purged periodically (and before a new one is created). `ccwm open` does not revoke the previous session.
- REST requests use `Authorization: Bearer <session token>`. Browsers never send this automatically, which handles CSRF. State-changing requests additionally require an allowed `Origin`.
- **TCP peer-UID verification:** on every accepted loopback TCP connection the daemon looks up the owner of the client's socket — the socket whose local address is the client's and whose remote address is the daemon's — with one exact `sock_diag` (`NETLINK_SOCK_DIAG`, `SOCK_DIAG_BY_FAMILY`) request for that 4-tuple; the reply must describe exactly that 4-tuple in a state other than `LISTEN`/`TIME_WAIT` (M4). A self-test at startup (a lookup of the daemon's own loopback connection) chooses the fallback, the row of `/proc/net/tcp`/`tcp6`, where `sock_diag` does not work; the method is reported as `peer_lookup` in `/service/status`. It serves the connection only if that UID equals the daemon's effective UID. The result is cached per connection (keep-alive requests inherit it), it is checked before any byte is read, and it fails closed (not found, ambiguous answers or a failed lookup mean "reject"). A leaked bootstrap or session token is therefore useless to another local user. This applies to every TCP endpoint, including `/health` and the static assets.
- **WebSocket:** the `Origin` is validated on upgrade. The client must send `{"type":"auth","token":…}` as its first message within 5 s, or the connection is closed with code 4401. No data is sent before authentication succeeds. **Existing connections are revalidated:** when a session token expires, is rotated out or is revoked, the daemon closes every WebSocket bound to it with code 4401: immediately on sign-out, revoke-all and the expired-session purge, and otherwise within 10 s (periodic revalidation). A revocation is acted on before any event that is waiting at the same moment, and a client that does not take a message within 5 s is disconnected, so a client that stops reading cannot delay the revalidation (v0.1.1, v0.1.0 review I3).
- **Revocation:** a "Sign out" button in the UI (revokes the current session) and `ccwm auth revoke-all` over the Unix socket (revokes every browser session).
- The server stores tokens **hashed** (SHA-256) and compares them in constant time. Tokens never appear in logs, error messages, URLs (apart from the single-use fragment) or the database in plaintext.
- Unauthenticated TCP endpoints (still subject to the peer-UID check): `GET /api/v1/health` (status, version and the Git commit the binary was built from), the static assets, and `POST /api/v1/auth/exchange`. A health response on TCP is **never** treated as proof of daemon identity; identity is established only over the Unix socket.

### 11.3 HTTP hardening
- Bind to `127.0.0.1` only. Non-loopback binding is not supported in v0.1.
- **Host validation:** accept only `127.0.0.1:<port>`, `localhost:<port>` and `[::1]:<port>` (DNS rebinding defense). Reject all others with 421/403.
- **Origin validation** for state-changing requests and WebSocket upgrades: it must equal `http://127.0.0.1:<port>`. TCP requests without an Origin are rejected for state-changing endpoints; the CLI uses the Unix socket instead. Any request to `/api/v1` that carries an Origin other than the allowed one is rejected, including GET.
- **CSP:** `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self' ws://127.0.0.1:<port>; worker-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. No inline scripts or styles, no `eval`, no workers.
- Also send `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on API responses, and `Cross-Origin-Opener-Policy: same-origin`.
- **Connection limits:** at most 64 concurrent TCP connections (a slot is taken before `accept`, so excess clients wait in the kernel backlog and cost no file descriptor) and a 10 s header-read timeout; a request body must arrive within 10 s of its head (`408 request_timeout`, connection closed). The Unix socket must stay usable while the TCP listener is saturated.
- Validate and canonicalize every path input. Project IDs are opaque and validated. Prevent path traversal and symlink escapes. Use parameterized SQL only. The config file and every ancestor of ccwm's directories must be owned by the user or root and not writable by other users (a root-owned sticky directory such as `/tmp` is acceptable; group write is acceptable only for the user's private group: the user's primary group, named like the user, with no other listed members). The check reads the owner and the mode bits; POSIX ACLs are not evaluated, which SECURITY.md documents as a limitation (v0.1.0 review L4).
- **Optional defense in depth:** mounting `/proc` with `hidepid=invisible` hides other users' command lines (where a sign-in link passed to the browser is visible). ccwm does not require it; the peer-UID check already makes a link seen there useless to another user.
- **Residual risks, documented in SECURITY.md:** an XSS bug could steal the `localStorage` token (mitigated by the no-`innerHTML` rule and the CSP); a same-user process can read everything; the bootstrap fragment briefly exists in the browser history (it is single-use and expires in 30 s); **an impostor that binds the port while the daemon is down can show a fake UI** (and read what the page stores in its origin) — the peer-UID check makes any token it obtains useless to the impostor's own connections, and `ccwm open` never talks to it; but what it stores in the browser for that origin (HTTP-cache entries, a service worker, `localStorage`) outlives it, and a script left there runs in the user's own browser, under the real daemon, until the origin's site data is cleared: the XSS residual without a bug in ccwm's page, not only a fake project list (SECURITY.md says what the user should do; `Clear-Site-Data` was evaluated and is not sent). **Any forwarder or proxy running as the user** (`ssh -L`, `socat`, IDE port forwarding) bypasses the peer-UID check (the check sees the forwarder, not the client behind it); never forward the ccwm port.

### 11.4 Data protection
- Data directory `0700`, files `0600`, process umask `0077`.
- Never log session content, prompts, tokens or credentials. Redact remote URLs in logs.

### 11.5 OS-level enforcement (best effort, reported)
- At startup, before discovery begins, the daemon applies a **Landlock** ruleset to itself. The ruleset is inherited by all child processes (`git`, `claude --version/--help`):
  - Read and execute allowed under the discovery roots, the Claude session directory, and the system paths needed to run `git`/`claude` (e.g. `/usr`, `/etc`, `/lib*`).
  - Write allowed **only** under ccwm's config, data, state and runtime directories.
  - Landlock ABI ≥ 4 (Linux 6.7+): deny all TCP `connect`, and allow TCP `bind` only on the configured port. Network confinement is reported as **TCP only**.
  - Landlock ABI ≥ 6: scope abstract Unix sockets and signals (`Scope::AbstractUnixSocket | Scope::Signal`), best effort and reported.
  - **Not confined by Landlock:** UDP (and other non-TCP socket families) and `connect()` on path-based Unix sockets (Landlock ABI ≤ 8 has no right for it). Every child process (`git`, `claude`) gets an environment without `DBUS_*`, `XDG_RUNTIME_DIR`, `SSH_AUTH_SOCK` and similar session-IPC variables.
  - **Seccomp (M4):** once the TCP and Unix listeners are bound, a seccomp filter is installed on every thread (TSYNC; inherited by later threads and children): `socket()` and `socketpair()` fail with `EPERM` for **every** address family, with no exception — the peer check's `NETLINK_SOCK_DIAG` socket (§11.2) is opened before the filter and reused, and whatever else needs a socket or a socket pair (the runtime's signal pipe) is created before it; `io_uring_setup`/`_enter`/`_register` (which can create sockets without `socket()`) and the x32 entry points of `socket`, `socketpair` and `io_uring_setup` are denied too. Only while it is active are UDP and path-based Unix-socket `connect()`/`sendto()` removed from the reported residual risks. Dependency: `seccompiler` (ARCHITECTURE §4).
  - **Daemon-level probes (M4):** after the listeners are bound, the daemon itself tries, from its blocking pool, a write outside its directories (an anonymous `O_TMPFILE` in the home directory, so an unconfined probe leaves nothing behind) and a TCP connect to `127.0.0.1:1`; after the seccomp filter, creating a UDP socket, a Unix socket and a Unix socket pair from a worker and a blocking-pool thread. A write that succeeds withdraws every Landlock claim, a connect that is not denied withdraws the TCP claim, a socket probe that is not denied withdraws the seccomp claim. A probe that fails for an **unexpected** reason (an error other than the expected denial, e.g. no `O_TMPFILE` support; the thread read probes included) proves nothing either way: that protection is reported as **`unverified`** — neither claimed nor withdrawn — in the report (`unverified[]`, apart from `unconfined[]`), in `ccwm status`, in `ccwm doctor` (a warning) and in the startup log. All results are in the report.
- The ruleset must be applied while the process is single-threaded: the daemon verifies that `/proc/self/task` has exactly one entry and otherwise reports `not_enforced`. After the async runtime starts, it probes a worker thread and a blocking-pool thread (a read outside the read set must fail with `EACCES`) and records the result in the report; a failed probe makes the report claim nothing.
- The config file's directory is **not** granted (the config is read before the sandbox is applied). The report flags any read rule that is `/` or an ancestor of the home directory.
- Use the highest ABI the kernel supports. If Landlock is unavailable or only partly supported, run anyway and report exactly which protections are active in `ccwm doctor`, `/service/status` and the startup log. Never claim a protection that isn't active.
- Apply systemd user-unit hardening only where verified to work in user units. Don't depend on `ProtectHome`/`ReadOnlyPaths`, which need user namespaces in user units and fail on some systems.
- **Dependency-level enforcement:** `cargo-deny` bans HTTP/network client crates (e.g. `reqwest`, `ureq`, `curl`, `hyper` client features, `hyper-util` client, `isahc`, `attohttpc`) and DNS resolver crates. CI fails if any appear in the dependency tree.
- Tests catch regressions; they cannot prove the absence of network activity. Document the guarantee in those terms.

## 12. REST and WebSocket API (v0.1)

Browser endpoints are served on TCP under `/api/v1`. CLI operations (bootstrap token, refresh, status, revoke-all) are served on the Unix socket with the same handlers and JSON contracts, authenticated by peer credentials, as JSON lines (for example `{"op":"auth.bootstrap"}` answered by `{"ok":{…}}` or `{"error":{"code":…,"message":…}}`) through the same service layer. The CLI endpoints are not reachable over TCP.

All endpoints live under `/api/v1`. They return JSON and use structured errors `{"error":{"code":"…","message":"…"}}` with correct status codes. All input is validated. Lists use opaque keyset cursor pagination (`limit` ≤ 200; the cursor encodes the sort key and the id). Contracts are documented in ARCHITECTURE.md.

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Liveness and version (unauthenticated; useful during initial discovery) |
| POST | `/auth/bootstrap` | **Unix socket only**: issue a single-use bootstrap token |
| POST | `/auth/exchange` | Bootstrap → session token |
| POST | `/auth/rotate` | Issue a new session token; the old one stays valid for 60 s |
| POST | `/auth/logout` | Revoke the current session |
| POST | `/auth/revoke-all` | **Unix socket only**: revoke all browser sessions |

## 13. CLI and service management (v0.1)

| Command | Behavior |
|---|---|
| `ccwm serve [--port N] [--config PATH]` | Run the daemon in the foreground. This is what systemd runs. |
| `ccwm start` / `stop` / `restart` | Wrap `systemctl --user … ccwm.service`. Clear error if the unit isn't installed. |
| `ccwm status` | systemd state plus a `/service/status` summary, including the Git commit of the daemon's build; warns when it differs from the CLI's own build. Sessions that belong to no project are broken down by reason and by the folders most of them were started in (e.g. `831 excluded (~/.claude-mem/observer-sessions)`; M3.1) |
| `ccwm open [--print]` | Get a bootstrap token and open or print the URL |
| `ccwm scan` | Trigger a refresh through the daemon over the Unix socket and report progress. **Never opens SQLite itself.** Errors clearly if no daemon is running. |
| (all CLI commands) | When the daemon's socket is not reachable, the CLI waits (up to 5 s) **only while the instance lock is held** (a daemon is starting); with no lock holder it fails immediately. When the reader of a command's output has gone (`ccwm status \| head`), the command ends quietly with status 0; it never panics on the closed pipe. |
| `ccwm doctor` | Checks: daemon running (verified over the Unix socket), port, inotify limits and usage, Git version, `claude` CLI and resume support, session directory found and readable, data directory permissions, active Landlock protections (filesystem/network, ABI level), lingering status. Suggests fixes and never applies them. |
| `ccwm service install` / `uninstall [--purge]` | Write or remove the user unit, then `daemon-reload` and `enable --now` / `disable --now`. Uninstall preserves data unless `--purge` is given (with a confirmation prompt). No sudo. |
| `ccwm auth revoke-all` | Revoke all browser sessions |
| `ccwm --help` / `--version` | Help text includes the unofficial-project notice |

- **Single instance:** use an `flock` on `$XDG_RUNTIME_DIR/ccwm/ccwm.lock` (released automatically when the process dies, so stale locks can't happen), plus `instance.json` (pid, port, version, start time). The CLI validates the instance only over the Unix socket, using peer credentials, never by a TCP health check. Only the daemon writes to the database.
- **Port collision:** fail fast with a clear message naming the port and suggesting `--port` or the Settings change. Use a dedicated exit code, listed in `RestartPreventExitStatus=`, so systemd doesn't restart-loop; "another instance holds the lock" gets its own dedicated code in the same list. Never auto-pick another port. Port is set by default 8765, `--port`, or the config file.
- **systemd user unit** (`~/.config/systemd/user/ccwm.service`): `ExecStart=%h/.local/bin/ccwm serve`, `Restart=on-failure`, `RestartSec=5`, `TimeoutStopSec=10`, `UMask=0077`, `Nice=10`, `IOSchedulingClass=idle`, `NoNewPrivileges=yes`, plus any other hardening directives verified to work in **user** units. `ProtectSystem=strict` and `ProtectHome=read-only` with `ReadWritePaths=` for ccwm's directories may be added as defense in depth only after the real daemon has been tested under them (M4); Landlock (§11.5) remains the primary enforcement. `PrivateDevices` is not used (it is rejected in user units). Logs go to journald. Graceful shutdown on SIGTERM flushes the database writer and closes watchers. **Verified (M4, systemd 255):** `ProtectSystem=`/`ProtectHome=`/`PrivateTmp=` make systemd run a user service in a user namespace where root-owned paths appear owned by `nobody` (65534), so the §11.3 ownership checks refuse to start: they are not used. The unit adds `Environment=PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin` (so the `claude` check finds Claude Code's usual install location) and the verified `LockPersonality`, `RestrictRealtime`, `RestrictSUIDSGID`, `RestrictNamespaces`, `SystemCallArchitectures=native`; not `MemoryDenyWriteExecute` (inherited by `claude --version`, a JIT runtime). **Memory limit (v0.1.1):** `MemoryMax=2G` with `MemorySwapMax=0`, a hard limit for the daemon and its children together, far above normal use (20–30 MiB) and above the worst case the ignore-rule limits of §5.2 allow (measured, docs/benchmarks.md; 2G is approved for now and is to be lowered, ROADMAP.md); at the limit the kernel kills the unit's largest process. `OOMPolicy=continue`: when that is a `git` or `claude` child, it fails like any other failed command and the daemon goes on (the default policy, `stop`, stopped the whole unit with it; verified with the real daemon in a transient user unit); a killed daemon is restarted. `StartLimitIntervalSec=10min` with `StartLimitBurst=10` (in `[Unit]`): a daemon that keeps failing ends in the `failed` state instead of being restarted for ever (with `RestartSec=5` the default start limit is never reached); starts by hand count too, `systemctl --user reset-failed ccwm` clears it (v0.1.1 review L4). Without `MemorySwapMax=0` the limit only moves the excess to swap (verified in a user unit on Ubuntu 24.04, systemd 255). It takes effect where the user manager has the cgroup memory controller; a drop-in (`systemctl --user edit ccwm`) changes it. Exit codes: **10** port in use, **11** another instance holds the lock; both in `RestartPreventExitStatus=`. `ccwm service install` refuses (before writing anything) when `~/.local/bin/ccwm` does not exist; `ccwm start|restart|service install` wait up to 10 s for the daemon to answer on its socket, `ccwm stop` up to 10 s for the lock to be released; `uninstall --purge` refuses while a daemon still holds the lock and removes exactly ccwm's config, data, state and runtime directories; `ccwm doctor` exits 1 when a check fails, and without a running daemon it reports only whether Landlock is in the kernel's LSM list (the ABI and active protections come from the daemon's report).
- **Scripts:** `scripts/install.sh` (copies the binary to `~/.local/bin`, runs `ccwm service install`, prints next steps) and `scripts/uninstall.sh`. Both are idempotent, run no privileged commands and preserve data by default.
- **Documentation:** start/stop/restart/enable/disable/status/logs (`journalctl --user -u ccwm -f`), manual foreground mode, and the difference between starting at login and starting at boot. For boot-before-login, document `loginctl enable-linger $USER`, which may require administrator authorization depending on polkit policy. Never run it automatically.

## 14. Storage and configuration (v0.1)

- **Locations (XDG):** config `$XDG_CONFIG_HOME/ccwm/config.toml`; database `$XDG_DATA_HOME/ccwm/ccwm.db`; state `$XDG_STATE_HOME/ccwm/`; lock, `instance.json` and the Unix socket in `$XDG_RUNTIME_DIR/ccwm/`. All are outside the monitored trees and always excluded.
- **Settings** live in `config.toml` (human-readable, written atomically, `0600`). The port must be readable before the database opens. The file is read at startup only; `PUT /settings` rewrites it atomically (comments are not preserved) and hand edits made while the daemon runs are overwritten. Runtime and derived data live in SQLite.
- **SQLite:** rusqlite with bundled SQLite, WAL mode, `foreign_keys=ON`, `busy_timeout`, embedded versioned migrations (`PRAGMA user_version`), and indexes on the sort and filter columns. **One dedicated writer thread** fed by a bounded channel with batched transactions. Reads run on a small pool of read-only connections via `spawn_blocking`. Synchronous SQLite calls never run on Tokio worker threads.
- **Tables (minimum):** projects, project_sources, file_events (bounded), git_cache, sessions, session_file_checkpoints, ignored_paths, auth_sessions (hashed), meta.
- Constraints prevent duplicate projects (unique canonical path) and repeated session ingestion (unique session ID; per-session aggregates are idempotent).

## 16. Testing (v0.1)

Rust unit and integration tests using temporary directories, temporary Git repositories and synthetic session fixtures. Never touch real user projects or `~/.claude` in tests. Use injectable roots and clocks. **No test creates files in the repository's working tree** (temporary directories live under `/tmp`): a ccwm watching the developer's home would register them as projects, and they turn into missing projects when the test deletes them (M3.1).

Coverage must include:
- Discovery: arbitrary home layouts, exact marker matching, symlinked markers, home and `~/.claude` exclusion, nested projects (Git and non-Git), session-cwd resolution (subdirectory cwd → project root), unassigned home sessions, deduplication, exclusions, symlink loops, `same_file_system`, inaccessible paths, explicit roots, ignore and un-ignore.
- Lifecycle: create, delete, rename and move (paired events and the fallback matcher), missing state, retention purge, a live marker creation appearing over WebSocket, creation outside watched areas found by reconciliation.
- Monitoring: non-recursive watch registration, watch budget enforcement, degraded mode, overflow recovery, debouncing, nested activity attribution, gitignored files ignored, no self-generated activity.
- Activity: bucket boundaries (0/1/6/7/29/30 days, across midnight and DST changes), the "this week" statistic, sort order including unknowns.
- Git: dirty/clean/untracked/staged, detached HEAD, worktrees, missing Git, `safe.directory` refusal, timeouts, remote URL sanitization, and **malicious configurations** (`core.fsmonitor` command, `core.hooksPath`, `diff.external`, textconv, a `core.pager`/`sshCommand` that would execute) asserting no execution, for example with a sentinel-file test.
- Sessions: incremental appends, partial trailing lines, truncation and rotation, malformed JSON, unknown types and fields, oversized lines, subagent records, tool-result "user" records excluded from the last prompt, deduplication across restarts, redaction, on-demand prompt reads bounded in size, no prompt text persisted while "Store prompt text" is off (the database scanned before and after clearing the index; a prompt read in flight while the setting turns off; a stale Settings save), early stop, duplicate session files, the container rule in both orders.
- Resume: UUID validation, adversarial path escaping, use of the recorded cwd, warning states.
- Security: auth flow (bootstrap single-use and expiry, exchange, rotation, logout, revoke-all), WebSocket auth timeout and no data before auth, WebSocket closed on token expiry and revocation, Host and Origin rejection, the CSP header present, path traversal attempts, privacy-mode field omission, Unix-socket peer-credential rejection (simulated mismatch), the CLI refusing to talk to an impostor (a TCP listener on the port with no valid socket).
- **Security acceptance tests** (required; each must exist and pass):
  1. Monitored project files are unchanged after discovery, watching and reconciliation (hash the full fixture tree, including mtimes and modes, before and after).
  2. Claude session files are unchanged (hash before and after parsing, clearing the index and uninstalling).
  3. `.git/index`, `.git/config` and refs are unchanged after every Git operation.
  4. Malicious Git configurations cannot execute commands: local-scope `core.fsmonitor`, clean/smudge/process filters activated by `.gitattributes`, `diff.external`, textconv, `core.pager`, `core.sshCommand`, `include`/`includeIf` pulling in any of these, and **promisor partial clones** whose `HEAD` object is missing, so that `status`/`log` would lazily fetch through the repository's transport (`ext::`, `file://` with `remote.<name>.uploadpack`, `ssh://` with `core.sshCommand`). Each is asserted with a sentinel file that must not appear, and each has a control run with a command ccwm actually runs (e.g. plain `git status`) that proves the vector executes without the mitigations.
  5. No external network connections: through a full discovery, live-watch, Git and session cycle, assert that the daemon and its Git subprocesses attempt no non-loopback connect: every `connect()` of the daemon and its children is traced with `strace` (`strace -f -e trace=connect,execve`) and checked. Without a usable `strace` the test is skipped with a notice (a failure in CI). Every `execve` of the daemon and its children is also checked against an allowlist: the daemon itself and `git` running `--version`, `rev-parse`, `status`, `log` or `config`; any `fetch`, `remote-*` helper, `sh` or `ssh` fails the test, and promisor partial clones in the fixture must start zero fetch children. There is **no network-namespace variant**: an unprivileged network namespace needs a user namespace, in which root-owned paths appear owned by `nobody`, so the §11.3 ownership checks refuse to start the daemon, and those checks are not weakened for a test. What `connect()` tracing cannot see (datagrams sent without a connect) is covered by the seccomp filter of §11.5, which is tested on its own. `cargo-deny` network-crate bans pass.
  6. Unauthorized access is rejected: no token, an expired token, a revoked token, a wrong Origin, a wrong Host, and a peer-UID mismatch on the Unix socket. A real cross-user check is documented as a manual procedure.
  7. Path traversal and symlink escapes are rejected in all path inputs and in marker reads.
  8. Logs contain no sensitive data: run with canary secrets planted in fixture prompts, tokens and remote URLs, and assert none appear in the captured logs at any level.
  9. Runtime data and credentials are excluded from Git: a CI check that `git check-ignore` matches the database, WAL/SHM, the socket, config, state and `*.jsonl` outside the fixtures.
  10. Clearing the session index, deleting the ccwm database (followed by a restart on the empty database that re-ingests every session file from byte 0, M3.1) and `ccwm service uninstall --purge` leave project and Claude data byte-identical.
  11. Landlock: on kernels that support it, a write outside ccwm's directories and an outbound connect from the daemon and from a Git subprocess are both denied.
- API: validation errors, pagination, settings round-trip, restart persistence.
- CLI and service: single-instance lock, port collision exit code, `scan` going through the API, graceful shutdown.
- UI: view toggle preserving search, sort and filters; theme and view persistence; privacy toggle. Use lightweight DOM tests where practical, or documented manual verification steps.

**Status:** phase 1 (verification and design) done on 2026-11-26. **The design is approved by the maintainer (2026-11-26)** with the decisions recorded in §21.12 (O9–O17); rules marked *(choice, for review)* were made while recording those decisions. **Phase 2 ran in two stops** (maintainer, 2026-11-26): **stop 1** — the plumbing (`ccwm hook`, the socket message and its validation, the process walk with the `CLAUDE_PID` cross-check, the open-session store with `/proc` liveness, persistence and restore, `ccwm hooks print`, the debug command `ccwm hooks events`) — then the O11 checks on the real home (§21.12; the facts in ARCHITECTURE.md §11a), which led to §21.2a (recorded facts from the session file), the elapsed time on "Needs approval" (§21.8) and the wider `argv[0]` rule (§21.5), all decided by the maintainer on 2026-11-26; then **stop 2** — the state machine, project resolution, the API, UI and Settings toggle, status and doctor lines, docs. **Built, 2026-11-26.** The facts it rests on were verified against the installed Claude Code **2.1.332** (ARCHITECTURE.md §11a; what was run, §13k): its hook documentation, the hook input schemas and code embedded in its binary, and one live `claude -p` run in a throwaway project under `/tmp` (approved by the maintainer). It extends §18's bullet and ARCHITECTURE.md §14.

### 21.1 Goal, principles, non-goals
- Show per project whether a Claude Code session is open there and whether Claude is **working** on a turn, **waiting** for the user's next prompt, or **needs approval** of a tool use. The sources are Claude Code hooks that **the user adds** (opt-in: without them nothing changes) and, for the ends of a turn no hook reports (an interrupt, a denial), the records Claude Code writes in the session file that §21.2a names — recorded facts, read by the session ingest ccwm already runs.
- The state is **never inferred** from file, Git or session-file activity (§5.3), and hook events are **never activity**: they move no activity time, no sort order (§5.4) and no watch or ignore-rule allocation (§5.1, §5.2).
- Unknown stays unknown: no state is derived from a timeout or guessed after a restart.
- Non-goals: no reading of transcripts for the indicator, no notifications or sounds, no control of Claude Code (ccwm never answers a prompt or a permission dialog, sends input or signals a process), no reading or editing of `~/.claude` settings or any other settings file.

### 21.2 Hook events (verified, Claude Code 2.1.332)

| Hook (matcher) | Fires when | Effect on the session |
|---|---|---|
| `SessionStart` | a session starts; `source` = `startup`, `resume`, `clear`, `fork` or `compact` | open, **waiting**; `compact` changes nothing (auto-compaction runs inside a turn) |
| `UserPromptSubmit` | a prompt is submitted (typed, `-p`/SDK, `/loop` and scheduled wake-ups, system turns) | **working** |
| `Notification` (matcher `permission_prompt`) | a permission dialog (a tool use, or a sandboxed command's network request) has waited about 6 s; in a terminal each keystroke defers it, and a dialog answered sooner sends nothing | **needs approval** |
| `PostToolUse`, `PostToolUseFailure` | a tool finished, or failed after it had started | from needs approval or unknown: **working**; otherwise nothing |
| `PostToolBatch` | every tool call of a batch has resolved, before the next model request | as `PostToolUse` |
| `Stop` | Claude finished responding — not on a user interrupt, not on an API error | **waiting** |
| `StopFailure` | the turn ended with an API error (instead of `Stop`) | **waiting** |
| `Notification` (matcher `idle_prompt`) | about 60 s after Claude finished, with no input since (interactive sessions only) | **waiting** |
| `SessionEnd` | the session ends; `reason` = `clear`, `resume`, `logout`, `prompt_input_exit` or `other` | **closed** |

- `StopFailure` keeps a turn that ended with an API error from showing "working" for good. **Verified on the real home (O11, 2026-11-26): no hook at all follows an interrupt** — Esc during a reply, "No" or Esc in a permission dialog, Esc while an approved tool runs: no `Stop`, `StopFailure`, `PostToolUseFailure` or `idle_prompt` (none for 3 minutes and more); `idle_prompt` fires exactly 60 s after a `Stop` only. These ends of a turn come from the session file (§21.2a). `permission_prompt` arrives about 6 s after the dialog appears (7.0 s after the prompt, measured).
- **Needs approval (O12; the matcher verified in the documentation and the binary):** the `Notification` matcher is the `notification_type`, and `permission_prompt` is one of its values. **No hook event marks the end of a permission wait** (the documentation names none). After an approval the tool runs, and the state leaves "needs approval" at the session's next tool event: `PostToolUse` or `PostToolUseFailure` when the approved tool finishes, `PostToolBatch` when its batch resolves. It also leaves at the next `UserPromptSubmit`, `Stop`, `StopFailure`, `idle_prompt` or `SessionEnd`. Consequences, documented: **an approved tool that runs long (a build, a test run) shows "needs approval" until it finishes**; a denial fires no tool event (`PermissionDenied` is for auto-mode denials only), so the state stays until the next prompt or the end of the turn.
- **An approval leaves no trace until the tool finishes** (O11, verified twice): neither a hook nor a session-file record is written between the approval and the tool's result; the result record (and `PostToolUse`) come when the tool ends. Hence the elapsed time on "Needs approval" (§21.8).
- Tool events from inside a subagent (`agent_id` present) are ignored *(choice, for review)*: otherwise a sibling subagent's tools would end another one's "needs approval".

### 21.2a Recorded facts from the session file (O11; maintainer decision 2026-11-26)
Claude Code writes the end of every turn the user ends into the session file, within about 10–60 ms of the key and on disk within about 250 ms (measured, 2.1.332). The session ingest (§7.2: the live watch on Claude Code's session folders, a 2 s debounce, incremental reads) hands the indicator two **facts** per session, each with the record's timestamp (milliseconds) and its `promptId` when the record has one (user records do, and it equals the hooks' `prompt_id` — verified; assistant and system records have none):
- **Interrupted**, from structural fields only: a `user` record carrying `interruptedMessageId` **and** `rowSource: "harness"` (Esc during a reply, Esc while an approved tool runs); a `user` record whose top-level `toolDenialKind` is `user-rejected` ("No" or Esc in a permission dialog, Esc while an approved tool runs); an `assistant` record with `isAbortedMidStream: true` (Esc during a reply). `rowSource: "harness"` alone is not enough (`/clear` and `/exit` write it too). Other `toolDenialKind` values do not end a turn *(choice, for review)*. Claude Code's fixed interruption strings (`[Request interrupted by user]`, `[Request interrupted by user for tool use]`) **corroborate only**: the parser never reads message text; the fixtures carry the strings, and a test checks that the structural rule finds an interruption in exactly the fixtures whose records carry one of them, for the same turn (the marker's `promptId`). `toolUseResult` stays unread (presence only, as in §7.1); its text is never used.
- **Turn ended**: a `system` record with `subtype: "turn_duration"` (written right after the `Stop` hooks): a backup for a lost `Stop`.
- **Allowlist:** the parser reads only the top-level `promptId`, `rowSource`, `interruptedMessageId` (presence), `toolDenialKind`, `isAbortedMidStream` and `subtype` in addition to §7.1's fields. Nothing new is stored: the facts go to the indicator in memory; `ccwm hooks events` lists them as the daemon's entries.
- **Which turn a fact belongs to:** a fact with a `promptId` applies only when it equals the session's current prompt id (from `UserPromptSubmit`); a fact without one, or a session whose current prompt id is not known (after a restart, hooks added during a turn), applies only when the record's timestamp is not older than the moment the session's current state was entered. A fact of an older turn (a file read again from byte 0, a late ingest after the next prompt) changes nothing.
- **Effect:** `working`, `needs_approval` or `unknown` → `waiting`; `waiting` stays.
- **Limits, documented:** the fact arrives after the debounce (about 2 s); when the session folder has no watch (the watch budget, §5.1), at the next reconciliation. A session whose first cwd names no project is read only up to that cwd (§7.2's early stop) and yields no facts — it shows no dot anyway. A Claude Code that stops writing these fields falls back to the hooks alone (the fixture tests fail first).

### 21.3 `ccwm hook <Event>` (the hook command)
- Run by Claude Code through the guarded command of §21.9 (`… && '<ccwm>' hook <Event>; exit 0`), with the event's name as its argument; reads the event JSON on stdin. It is **dispatched before argument parsing**, and anything after the event name is ignored. The argument must equal the input's `hook_event_name`; otherwise nothing is sent.
- **Always exits 0 and never writes to stdout.** Claude Code adds the stdout of a `SessionStart` or `UserPromptSubmit` hook to the model's context, and reads exit code 2 as "block the prompt" (`UserPromptSubmit`) or "keep working" (`Stop`). A failure writes one line to stderr (visible in `claude --debug hooks`), never input content. Stdin a terminal (run by hand): a one-line hint on stderr, exit 0.
- **Hard budget:** the socket exchange — connect, send, and the daemon's one-line acknowledgement — gets **at most 100 ms**; past it the command exits 0 silently, whatever happened. The client waits for the acknowledgement inside that budget because the daemon checks the client's ancestry in `/proc` while the client still runs (§21.5): a client that left right after sending would be refused. Stdin is read up to **16 MiB**; a watchdog ends the whole command with status 0 after 1 s, so a stdin that never closes cannot hold Claude Code.
- **Allowlist parsing:** only `hook_event_name`, `session_id`, `cwd`, `prompt_id`, `source` (SessionStart), `notification_type` (Notification) and the presence of `agent_id` are read. Every other field — the prompt text (`prompt`), the assistant's last message (`last_assistant_message`), the tool fields (`tool_name`, `tool_input`, `tool_response`, `tool_calls`, `error`), `background_tasks` (shell commands), `session_crons` (prompts), `session_title`, `transcript_path`, `model`, `permission_mode`, `effort`, anything unknown — is skipped by the parser without being materialized, **never sent and never logged**.
- `CLAUDE_PID` (set by Claude Code 2.1.332 for hook commands; the hook documentation does not mention it) is read and sent when present and valid (decimal digits, no sign or leading zero, 2 to 4,194,304), as a cross-check (§21.5). No other variable of the hook's environment is read — it holds Claude Code's own tokens — except those every ccwm command uses to locate its directories and socket (`HOME`, `XDG_RUNTIME_DIR`, `XDG_STATE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `CLAUDE_CONFIG_DIR`); the passwd entry is consulted only when `$HOME` does not qualify (§4.1).
- Parsing stops at the end of the first JSON value (a stdin left open after the event holds nothing up). Skipped fields are skipped without recursion (any nesting depth) and without being decoded.
- Sends nothing (exit 0) for: a `Notification` other than `idle_prompt` or `permission_prompt`; any other event that carries `agent_id` (from inside a subagent); an event name not in §21.2 or not equal to the argument; malformed or oversized input. *(Reading, for review, made in stop 1: "any other event" excludes `Notification` — a `permission_prompt` or `idle_prompt` that carries `agent_id` is sent, because a subagent's permission dialog blocks the whole session.)*
- Sends exactly one `hook.event` request over the Unix socket (§11.2, the daemon's UID verified first, like every CLI command) and reads one response. **It never waits for a starting daemon and never retries** (the 5 s wait of §13 does not apply): no daemon ⇒ exit at once. It opens no config file and no database and writes no file.

### 21.4 The socket message
`{"op":"hook.event","event":…,"session_id":…,"cwd":…,"claude_pid":…,"prompt_id":…,"source":…,"notification_type":…}`, answered by `{"ok":{"accepted":true}}` or an `invalid_argument` error naming the reason (§21.10).
- Exact key set: `source` for `SessionStart` only (required there), `notification_type` for `Notification` only (required there: `idle_prompt` or `permission_prompt`), `prompt_id` and `claude_pid` optional, no other key; the object's shape is checked by hand like every op.
- `event`: one of the nine names of §21.2. `session_id`, `prompt_id`: lower-case UUIDs (§7.1, §8). `cwd`: absolute, at most 4,096 bytes, no NUL. `claude_pid`: an integer from 2 to 4,194,304, not the daemon's own pid. `source`: `startup`, `resume`, `clear`, `compact` or `fork`.
- **The request limit of the socket is 32 KiB** for every op (was 4 KiB; a cwd of 4,096 bytes, JSON-escaped, does not fit in 4 KiB).
- The `cwd` is the **only path a socket client ever sends** (O14). It is handled exactly like a cwd recorded in a session file: untrusted, resolved with the rules of §4.4 inside the sandbox, never opened for content, never logged.

### 21.5 Who may report, and which process is the session's (O10)
- The peer-UID check of §11.2 applies, unchanged.
- **The daemon finds the Claude Code process itself**; it never relies on the client's word alone. While the client waits for its reply, the daemon takes the client's pid from `SO_PEERCRED` and walks up the parent chain through `/proc/<pid>/status` (`PPid`): at most 8 steps, only through processes whose real and effective UID are the daemon's (the walk stops at the first that is not, and at pid 1), and only through parents that started no later than their child (a later start time means the pid was reused; *added in stop 1, for review*). The session's process is the **nearest** ancestor whose `/proc/<pid>/cmdline` identifies Claude Code, by `argv[0]` (maintainer decision after O11, 2026-11-26): (1) its last path component is exactly `claude` (a session started as `claude`); (2) it starts with `claude ` — a process title Claude Code writes over its arguments, e.g. `claude bg-pty-host`, `claude bg-spare`; (3) it is Claude Code's versioned binary, a path ending in `/claude/versions/<version>` (digits and dots). No such ancestor ⇒ refused (`no_claude_ancestor`). The chain of a terminal session: hook command → `sh` → `claude`. **A background session** (`claude --bg`, O11): supervisor (`argv[0]` `~/.local/bin/claude`) → `claude bg-pty-host` → the session process (`claude bg-spare`, or the versioned binary for one resumed in the background) → `sh` → hook; with rule 1 alone the walk passed the session and stopped at the supervisor, and every event was refused `pid_mismatch` (`CLAUDE_PID` is the session process). `CLAUDE_PID` is not trusted beyond the walk: it must still equal the nearest identified process.
- **`CLAUDE_PID`, when sent, must equal that process**; otherwise the event is refused (`pid_mismatch`). Without `CLAUDE_PID` the walk's result is used. Both paths are tested.
- **Identity** of the process: (pid, start time — field 22 of `/proc/<pid>/stat` —, boot id — `/proc/sys/kernel/random/boot_id`), read at the event. It protects against a reused pid and against a reboot.
- **Interactive or not (O17):** the same `cmdline` tells whether the session is non-interactive: an argument `-p` or `--print`, or `--output-format` / `--input-format` (with or without `=value`; per `claude --help` both work only with `--print`), before any `--` *(choice, for review: combined short options such as `-cp` are not recognized)*. Non-interactive sessions — `-p` runs, and SDK hosts that start the CLI that way (observed: `--output-format … --input-format …` without `-p`) — are tracked but **hidden by default** (§21.8). Background sessions are interactive (shown): they can be attached.
- **Scope, honestly:** same-user processes are outside the threat model (§11.1) and can still forge events (a child can name its parent `claude`). The check stops stale or garbage pids and reports from outside a Claude Code process tree; it is not a defence against a process running as the user.
- **Sandbox:** nothing changes. Under ccwm's Landlock policy (ABI 8) and seccomp filter, `status`, `stat` and `cmdline` of processes outside the domain stay readable; `exe`, `cwd` and `environ` fail with `EACCES` (verified, ARCHITECTURE.md §13k). No new socket, no new Landlock rule.

### 21.6 States and rules
| State (per open session) | Meaning | Entered by |
|---|---|---|
| `needs_approval` | Claude waits for the user to approve a tool use or a network request | `Notification` `permission_prompt` |
| `working` | Claude is working on a turn | `UserPromptSubmit`; a tool event in `needs_approval` or `unknown` |
| `waiting` | open; Claude is idle and waiting for the user's next prompt | `SessionStart` (not `compact`), `Stop`, `StopFailure`, `Notification` `idle_prompt` |
| `unknown` | open (the process is alive), activity not known | a daemon restart (§21.7); a first event `SessionStart` with `compact` |
| closed | not tracked: no dot | `SessionEnd`; the process is gone |

- **Any event opens** a session id that is not tracked (hooks added in the middle of a session, a daemon that was down), except `SessionEnd`; a tool event opens it as `working`.
- A tool event in `waiting` changes nothing *(choice, for review)*: a turn that ended stays ended until the next prompt.
- **Stale events:** `UserPromptSubmit` records the session's current `prompt_id`; any other event whose `prompt_id` is present and differs from it changes nothing and is counted (`stale`; for example an idle notification that arrives after a newer prompt). `SessionStart` and `SessionEnd` are never stale; `SessionStart` forgets the current prompt id.
- **Recorded facts** (§21.2a): interrupted or turn ended → `waiting`, from `working`, `needs_approval` or `unknown`, for the current turn only.
- `SessionStart` for a tracked id takes the new process identity (a session resumed by a new process, a respawned background session). One process may hold several sessions; each is tracked on its own.
- **Liveness (O13):** a session is closed when its process is gone — no `/proc` entry, another start time or boot id, or the state `Z`/`X` — checked at every event, at start (§21.7) and **every 5 s** while any session is tracked. No time limit on any state.
- Each state change records the time (`since`, whole seconds).
- **Project (O14):** the cwd of the session's first event, validated like a session cwd and resolved with §4.4 (canonical path, roots, exclusions, nested rule, session-only rule). A session whose cwd names no registered project stays tracked as unassigned (counted by reason, §21.10) and is resolved again when projects are added, removed or moved and at each reconciliation. **Hook events never register a project**: the session file does (§4.3).
- At most 256 tracked sessions; events that would open more are refused (`limit`).

### 21.7 Restart behaviour
- **Daemon restart:** tracked sessions are persisted (session id, pid, start time, boot id, the first cwd, the time opened; never prompt text, titles or states). At start each is restored if its process is alive with the same start time and boot id and its `cmdline` still identifies Claude Code (§21.5; interactive or not is read again), in the state `unknown` until its next hook event; the others are deleted. The state is never guessed.
- **Reboot:** the boot id differs; every persisted session is dropped.
- **Claude Code restarts a session in a new process** (`claude respawn`, `--resume`): its `SessionStart` replaces the identity.
- A hook event that is lost (the 100 ms budget ran out, the hook timed out) leaves the last known state until the session's next event; this is documented.
- **"Clear session index"** (§7.3) also deletes the persisted open sessions and empties the tracker (O16); sessions come back with their next hook event.

(maintainer decision after O11, 2026-11-26) *(steady, and the colour: choice, for review)*;

### 21.9 Hook configuration (documented; the user adds it)
- **`ccwm hooks print`** prints, on stdout and nothing else, the `hooks` object to merge into a Claude Code settings file: one entry per event of §21.2 (`Notification` twice, one per matcher), each `{"type":"command","command":"command -v '<ccwm>' >/dev/null 2>&1 && '<ccwm>' hook <Event>; exit 0","timeout":5}`. `<ccwm>` is the running binary's canonical path, POSIX-quoted (§8) and then JSON-encoded; a path with characters that §8 refuses for a terminal is refused; a warning goes to stderr when the binary is not `~/.local/bin/ccwm`. **The guard makes the hook safe when ccwm is missing or broken:** a missing ccwm is not called, and `exit 0` ends the shell with status 0 whatever ccwm did, with nothing on stdout (checked with dash: a missing path is skipped, the snippet exits 0). The documentation also gives the `PATH` form, `command -v ccwm >/dev/null 2>&1 && ccwm hook <Event>; exit 0`, for a `ccwm` on Claude Code's `PATH`. The hooks stay synchronous, not `async`: Claude Code waits for a synchronous hook before it goes on, which keeps a session's turn events in order (a late `Notification` is caught by the `prompt_id` rule of §21.6), and `-p` kills async hooks at teardown. Example:
  ```json
  {"hooks": {
    "SessionStart":       [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook SessionStart; exit 0"}]}],
    "UserPromptSubmit":   [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook UserPromptSubmit; exit 0"}]}],
    "Notification":       [{"matcher": "permission_prompt", "hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook Notification; exit 0"}]},
                           {"matcher": "idle_prompt", "hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook Notification; exit 0"}]}],
    "PostToolUse":        [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook PostToolUse; exit 0"}]}],
    "PostToolUseFailure": [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook PostToolUseFailure; exit 0"}]}],
    "PostToolBatch":      [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook PostToolBatch; exit 0"}]}],
    "Stop":               [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook Stop; exit 0"}]}],
    "StopFailure":        [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook StopFailure; exit 0"}]}],
    "SessionEnd":         [{"hooks": [{"type": "command", "timeout": 5, "command": "command -v '/home/USER/.local/bin/ccwm' >/dev/null 2>&1 && '/home/USER/.local/bin/ccwm' hook SessionEnd; exit 0"}]}]
  }}
  ```
- **ccwm never reads or edits** `~/.claude/settings.json` or any other settings file. The documentation says where the snippet goes: `~/.claude/settings.json` for every project, or a project's `.claude/settings.local.json` for one; hook entries merge across settings files, and an identical handler in several files runs once.
- **Cost:** `PostToolUse`/`PostToolUseFailure` and `PostToolBatch` run the hook after every tool call and every batch: one process start and one socket round trip each (a few milliseconds; the socket part at most 100 ms).
- **Documented limitations:** no hook runs under `claude --bare`, `--safe-mode`, `--restricted` (user, project and local settings are ignored), `disableAllHooks`, a managed `allowManagedHooksOnly`, or, in an interactive session, before the workspace trust dialog is accepted. A Claude Code started under another name (for example through the versioned binary's own path) or in another PID namespace (a container) is not found by the walk (`no_claude_ancestor`). A shell whose runtime directory differs from the daemon's (§11.2) reaches no daemon. With ccwm uninstalled the hooks do nothing until the user removes them.

### 21.10 Status, privacy, security
- **`ccwm hooks events [--follow]`** (a debugging aid; maintainer request 2026-11-26, for O11; built in stop 1): the daemon keeps the **last 256** hook events in memory — never persisted, empty after a restart — and the command lists them oldest first, with the counters (received, refused by reason, open sessions and how many are non-interactive): sequence number, local time with milliseconds, the event name with `SessionStart`'s `source` or `Notification`'s `notification_type`, the session id, whether `CLAUDE_PID` was sent, and the outcome (`opened`, `opened (non-interactive)`, `accepted`, `new process`, `closed`, `ignored (not open)`, `refused: <reason>`), plus what the daemon did on its own (`closed: process gone`, `restored`, `dropped at start: process gone`, `cleared: …`). **Names, times and session ids only**: no cwd, pid, `cmdline` or text from a session. Socket op `hooks.events` only (no HTTP endpoint). `--follow` asks again every 300 ms and says when the daemon restarted. Events the hook command does not send (§21.3) never appear.
- **`ccwm status`** and `/service/status` (`hooks`): open sessions by state, hidden non-interactive ones, unassigned ones by reason, the time of the last event, events received, stale events, refused events by reason (`malformed`, `no_claude_ancestor`, `pid_mismatch`, `limit`), and the recorded facts applied from session files (§21.2a). **`ccwm doctor`**: an informational line — the last event, or "no hook event since the daemon started (`ccwm hooks print`)"; never a failure (hooks are opt-in); it reads no settings file.
- **Privacy (§14 proposal 3, approved):** the indicator stays visible in privacy mode; its payload is states, counts and times only — no path, no pid, no text from sessions. Prompt text, the assistant's text and the tool fields never leave the hook process (§21.3). Logs carry the event name at `trace` level only, never the cwd. Persisted sessions hold the first cwd (like session rows) and are deleted when the session closes (`secure_delete`, §7.3).
- **Security:** §21.4 and §21.5. The daemon starts no process, opens no socket and gets no new sandbox rule for the indicator; `ccwm hook` runs outside the daemon, as the user, like every CLI command.

## Appendix B — Assumptions and verdicts

Verdicts were recorded on 2026-11-23 on the development host (Ubuntu 24.04.4, Linux 7.0.0-34, git 2.43.0, Claude Code 2.1.331). Session-schema facts come from a structural inspection of the maintainer's session directory (key paths, value types and low-cardinality discriminators only; accepted by the maintainer). Further session-schema inspection follows §19.

| # | Assumption | Verdict |
|---|---|---|
| 1 | Claude Code session files are JSONL under `<config dir>/projects/*/`, and records carry `sessionId`, `cwd`, `timestamp` and `type` fields, plus some way to tell genuine user prompts from tool results and meta records. | **Partly true.** Layout, `sessionId` (equals the file stem) and ISO-8601 `timestamp` are confirmed. `cwd` exists only on `user`, `assistant`, `attachment` and `system` records. Timestamps are not ordered within a file. No single flag identifies genuine prompts: `promptSource`/`turnOrigin`/`isMeta`/`isCompactSummary`/`toolUseResult` combine, and some records lack `promptSource` (§7.3). Subagent files sit deeper, in `<session-id>/subagents/`. |
| 2 | `claude --resume <session-id>` is the resume syntax and must be run from the session's original cwd. | **Syntax confirmed** in `claude --help` (2.1.331). The cwd requirement is **untested** (running it starts an interactive session) and inferred from the directory naming. |
| 3 | `CLAUDE_CONFIG_DIR` overrides the default `~/.claude` location. | **Not verifiable on this host** (the variable is unset); the string occurs in the `claude` binary. Treated as true; tests inject the root. |
