# v0.2.0 review (the changes since v0.1.1)

Review of `git diff v0.1.1..HEAD` (`972f083..72b1a70`): the design commit `9909784` and the two build
commits `7ef464f` (stop 1: `ccwm hook`, the open-session store, `hooks events`) and `72b1a70` (stop 2:
states, recorded facts, project resolution, API/UI). I did not write this code. Scope per the brief: the
hook socket message (validation, size limits), the ancestry walk and the `CLAUDE_PID` check (spoofing by a
process of the same or another user, pid reuse), the 100 ms / 1 s budgets (can a hook block or slow
Claude Code, or print to stdout), the wider session-file allowlist (`toolUseResult` and message text must
stay unread), the state machine (stale prompt ids, restarts, many sessions), privacy mode, the printed
snippet when ccwm is missing, and whether the new tests fail without their fix.

**Method.** I read the diff of every source and test file, and the new parts of `REQUIREMENTS.md` §21,
`ARCHITECTURE.md` §11a/§15, `SECURITY.md`, `CHANGELOG.md` and `docs/session-hooks.md`. Everything I ran
used a clone of `72b1a70` in the session's temporary folder:

- **Baseline:** `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings` and
  `CCWM_REQUIRE_LANDLOCK=1 CCWM_REQUIRE_LANDLOCK_ABI=8 CCWM_REQUIRE_INOTIFY=1 cargo test` are green (315
  unit tests and every integration suite, `tests/ui.rs` under node included).
- **Mutations:** 51 changes, each taking one check or one fix out, followed by the unit tests and, if they
  missed it, `tests/{hooks,live_api,ipc,sessions_api,ui,http}.rs`. Two combined controls on top of that.
  See "Do the new tests fail without their fix?".
- **Experiments:** six: two scratch store tests (E1, E2), `strace` of `ccwm hook` (E3), timing of a 16 MiB
  prompt with the debug and release builds (E4), the guarded command under `dash` with odd `ccwm` paths
  (E5), and a proposed test against the surviving allowlist mutation (E6). The appendix says how.

A finding marked **demonstrated** was run; one marked **reasoned** comes from the code alone. Nothing about
Claude Code's own behaviour was run (no `claude` was started); where a finding depends on it, it says so.

**Constraints honoured.** No repository file was changed except this document. `~/.claude` and
`$CLAUDE_CONFIG_DIR` were never opened. Nothing was pushed or tagged. The one synthetic environment
(`/tmp/ccwm-rv-e3`, removed afterwards) was used without a daemon; the maintainer's `ccwm.service` was not
touched. Scratch tests and mutations lived only in the clone and were reverted after each run.

**Verdict.** No Critical, High or Medium finding. The parts the brief singled out hold: the socket message
is checked by hand against the exact key set and bounds of §21.4, and 32 KiB fits the worst case; the
walk is bounded, stays inside the user's own processes and refuses a `CLAUDE_PID` that names anything
but the nearest Claude Code process; `ccwm hook` exits 0 on every path, never writes to stdout, and is
capped at 1 s whatever happens (0.19 s for a 16 MiB prompt with the release build); privacy mode gets
states, counts and times only. 48 of the 51 mutations are caught, most by focused unit tests. The
findings are about the edges of the state machine (which process may end a session, and what a lost
`SessionEnd` leaves behind), two design choices that misreport common workflows, one spec statement the
hook command does not meet (NSS lookups), and one gap in the tests that guard the allowlist.

## Low

### L1. `SessionEnd` from any Claude Code process closes the session

`Store::apply` (`src/presence/store.rs:382-391`) removes the session on `SessionEnd` without looking at
which process sent it. Any other event from a process that is not the session's current one is applied
too: `moved` is false (`:417-418`), and the event still changes the state. The stale rule only catches
it when both sides carry different prompt ids.

When it happens: the same session id open in two processes at once, which `claude --resume <id>` (or
the resume picker) in a second terminal produces while the first still runs. `SessionStart(resume)` from
B moves the session to B (correct, §21.6). When the user later leaves A (`/exit`, Ctrl-D), A's
`SessionEnd` closes the session although B is working on it or waiting for input. It comes back only with
B's next event: a "waiting" session disappears from the cards, the counts and the "Waiting for me" filter
until the user types in B again.

**Demonstrated** with a scratch test in the clone (E1): `SessionStart` from pid 10, `SessionStart(resume)`
from pid 20, `UserPromptSubmit` from 20, then `SessionEnd` from 10 ⇒ `Outcome::Closed`, nothing tracked.
The existing test `session_start_moves_a_session_to_its_new_process` pins the related behaviour that a
live non-owner's `UserPromptSubmit` changes the state (`Changed(Working)`).

**Suggested fix:** apply `SessionEnd` only when it comes from the session's current process, or when that
process is gone (the same `alive` check `moved` uses), and log it as `ignored (another process)`
otherwise. Whether other events from a non-owner should apply is a choice; ignoring them unless they carry
the current prompt id would be consistent with the stale rule. A store test for each case.

### L2. A lost `SessionEnd` leaves a ghost session for the life of its process

`/clear` ends session X and starts Y in the **same** process (`SessionEnd` X, `SessionStart(clear)` Y);
`/resume` inside a running session does the same. If X's `SessionEnd` is lost (the daemon was stopped or
restarting, the 100 ms budget ran out), nothing ever closes X: the sweep keeps it because its process is
alive (`Presence::sweep`, `src/presence/mod.rs:331`), and a daemon restart restores it because restore
checks the process, not the session (`ProcFs::still_claude`, `src/presence/proc.rs:266`). The project then
shows two open sessions — one of them a ghost in its last state, or "Session open" after a restart — until
the user leaves Claude Code. §21.7 documents that a lost event "leaves the last known state until the
session's next event"; for X there is no next event.

**Demonstrated** at the store level (E2): X opened by pid 10, its `SessionEnd` dropped, Y opened by
`SessionStart(clear)` from pid 10 ⇒ the project's aggregate counts 2 sessions, both waiting, and both stay
in the sweep's list. The restart case is reasoned from `restore` (`src/presence/mod.rs:370-406`).

Interplay with SECURITY.md (`:266`) and §21.10: the persisted first cwd is "deleted when the session
closes"; for a ghost it stays until the process exits and the daemon starts again.

**Suggested fix (a choice):** when `SessionStart` with `source` `clear` or `resume` arrives from process P,
close the other sessions held by P (a terminal Claude Code holds one session at a time; whether an SDK host
can hold several at once — the reason for "one process may hold several sessions" — would need checking).
At least document the ghost in docs/session-hooks.md.

### L3. A user's own blocking Stop hook leaves the session "waiting" while Claude works

`Stop` sets `waiting` (`next_state`, `src/presence/store.rs:84`), and a tool event in `waiting` changes
nothing (`:88-91`, the *(choice, for review)* of §21.6). Claude Code runs the hooks of one event together;
when another `Stop` hook returns exit 2 (or `{"decision":"block"}`), Claude keeps working — a common
pattern for "keep going until the tests pass" hooks and several plugins. ccwm's own `Stop` hook has
already reported `waiting`, and every `PostToolUse`/`PostToolBatch` of the continued turn is ignored, so
the card says "Waiting for input" while Claude runs tools, until the continuation's own `Stop`. No
`UserPromptSubmit` follows a blocked stop, so nothing else moves it.

**Reasoned**, and it rests on Claude Code behaviour I did not run: that a blocked stop continues the turn
without a new prompt (documented for hooks), and that the continuation's tool events carry the same
`prompt_id` (not verified). The `Stop` input has `stop_hook_active` (`tests/fixtures/hooks/2.1.332/Stop.json`)
but it marks the second stop, not the first.

**Suggested fix:** let a tool event move `waiting` → `working` when its `prompt_id` equals the session's
current one (the stale rule already drops tool events of older turns, which seems to be what the choice
guards against). Worth an O11-style check with a blocking Stop hook in the throwaway project first.

### L4. An approval inside a subagent shows "Needs approval" until the subagent finishes

Two choices meet here: a `Notification` with `agent_id` is sent (a subagent's permission dialog blocks the
session, §21.3), but tool events with `agent_id` are not (`Report::from_hook`,
`src/claude/hook.rs:321-335`). After the user approves a tool inside a subagent, the next event the daemon
sees from the main thread is the `Task` tool's `PostToolUse` when the **whole subagent** ends — which can
be many minutes. The documented limit (§21.2: "an approved tool that runs long shows needs approval until it
finishes") understates this case; the "Needs approval · N min" counter keeps counting the whole time.

**Reasoned.** The stated reason for dropping subagent tool events — a sibling subagent's tool ending
another one's "needs approval" — is real, but showing a stale approval for the whole subagent is the more
common outcome. **Suggested fix (a choice):** send subagent tool events with an `agent` flag and let them
move only `needs_approval` → `working` (any tool event after the dialog means some approval went through);
or document this case in §21.2 and docs/session-hooks.md.

### L5. `ccwm hook` looks up the passwd and group entries on every event

The v0.2 change to `paths::current_home` (`src/paths.rs:360`) skips the passwd lookup when `$HOME`
qualifies, "too slow for `ccwm hook` (§21.3)"; §21.3 and `CHANGELOG.md:48` say the passwd entry is
consulted only when `$HOME` does not qualify. But `hook_problem` → `daemon_socket` (`src/cli.rs:412-415`)
→ `Owner::current(uid)` → `paths::private_group` (`src/paths.rs:303-308`) calls `getpwuid` **and**
`getgrgid` unconditionally, on every event.

**Demonstrated** (E3): `strace` of the debug build running `ccwm hook Stop` in a synthetic environment
shows `/etc/nsswitch.conf`, `/etc/passwd` and `/etc/group` opened and two connection attempts to nscd's
socket. This host's `nsswitch.conf` lists `files systemd sss` for both; for a user found in `files` it is
fast, but on a directory-service host the lookups go to sssd/LDAP before the 100 ms budget even starts
(the watchdog still caps the hook at 1 s). The release binary is musl, which reads the files and asks nscd
only, so there the cost is small — but the statement in the spec is still not what the code does.

**Suggested fix:** for `ccwm hook`, verify the runtime directory without the private-group lookup (it only
loosens what group write is accepted; a strict "no group or other write" check needs no lookup), or
resolve it lazily only when a directory is group-writable. A test that runs `ccwm hook` under `strace`
(test 5 already uses `strace`) and asserts that `/etc/passwd` and `/etc/group` stay unopened when `$HOME`
qualifies.

### L6. No test fails if the parser starts decoding `toolUseResult` or `message`

The brief's requirement — `toolUseResult` and message text must stay unread — is met by the code: `Head`
(`src/claude/record.rs`) declares only top-level scalar fields, and the six new ones are `promptId`,
`rowSource`, `interruptedMessageId` (presence, `IgnoredAny`), `toolDenialKind`, `isAbortedMidStream` and
`subtype`. But nothing **guards** it. Mutation F2 adds
`toolUseResult: Option<String>` (lenient) and `message: Option<serde_json::Value>` to `Head`, and every unit
and integration test still passes. `turn_records_leave_their_text_unread` checks the parser's **output**
for canaries, which a field that is decoded and then dropped never reaches.

`src/claude/hook.rs` already has the right technique (mutation H6, the same change to `HookInput`, is
caught by `hostile_and_malformed_inputs_send_nothing`): serde_json does not validate UTF-8 inside a skipped
string, so raw invalid UTF-8 inside a skipped field parses, while a decoded one makes the record fail.

**Demonstrated** (E6): a scratch test that writes a `user` record with raw `\xff\xfe` bytes inside
`toolUseResult` and inside `message.content`, and asserts `lines == 1, malformed == 0` and a fact, passes on
`72b1a70` and fails under F2. Suggested: add it to `src/claude/parse.rs` (the same for the §7.1 fields of
other record types, if not already covered).

### L7. The walk does not check that the client is still the process that connected

`Presence::report` (`src/presence/mod.rs:172-178`) walks from the pid `SO_PEERCRED` recorded at
`connect()`. The client waits at most 100 ms for its answer. When the daemon handles the request later (a
busy runtime; the request stays readable in the socket buffer after the client left), the pid may belong
to nobody — the event is refused `no_claude_ancestor` and counted as a refusal, which misleads the
counters — or, after a reuse, to an unrelated process whose ancestry is then walked. The start-time rule of
§21.5 protects the parents, not the peer itself.

**Reasoned**; pid reuse within that window is unlikely (`pid_max` 4,194,304), so this is about honest
counters more than spoofing. **Suggested fix:** before the walk, check that the client has not hung up
(`poll` for `POLLRDHUP` on the connection; no new socket needed), and refuse with a distinct reason
(`client_gone`) if it has; or compare the peer's start time with the connection's accept time.

### L8. Project resolution is spawned per opened session, uncoalesced

`Service::hook_event` sends `Control::ResolveSessions` for every `Opened`/`NewProcess` outcome, and
`Service::control` (`src/service.rs:942`) spawns a task per control. Each task runs
`Tracker::resolve_open_sessions` (`src/tracker/mod.rs:162`): a query of every project and a
`spawn_blocking` that resolves **every** open session's cwd. A parallel fan-out of `claude -p` runs (common
in scripts and SDK hosts; hidden, but tracked) makes N tasks doing O(N) resolutions each, with up to N
concurrent blocking threads — the pattern ARCHITECTURE.md's M4 gotcha warns about (the blocking pool grows
with concurrent `spawn_blocking`). The tasks also finish in any order: one that took its snapshot before a
project was registered can assign `not_registered` after a newer one assigned the project; the session then
has no project until the next resolution (the next reconciliation).

**Reasoned.** Bounded by the 256-session limit, so not a resource problem in practice. **Suggested fix:** a
coalescing flag (as `request_refresh` does for reconciliations): at most one resolution running and one
pending, each starting from the current state.

## Info

- **I1. The snippet does not discard ccwm's stdout.** The guard makes the shell exit 0 and skips a missing
  ccwm (demonstrated with `dash`, E5: a missing path, a non-executable file and a directory all exit 0 with
  empty stdout). A ccwm path that runs something else — an older or foreign binary, a stand-in — still
  writes into the model's context for `SessionStart`/`UserPromptSubmit`: the E5 stand-in that prints `OUT`
  and exits 2 gives status 0 and stdout `OUT`. §21.9 and its test pin this ("empty stdout wherever ccwm is
  real or missing"). Adding `>/dev/null` to the ccwm call (`… hook <Event> >/dev/null; exit 0`) costs
  nothing, since ccwm never writes to stdout, and covers the broken case too.
- **I2. Symlinked installs.** `ccwm hooks print` writes the binary's canonical path (`src/cli.rs:255`;
  `current_exe` is already resolved on Linux). With `~/.local/bin/ccwm` a symlink to a versioned file, the
  snippet names the versioned file, no warning is printed (both canonicalize to it), and an upgrade that
  moves the symlink leaves the hooks calling a path that no longer exists — which the guard then skips
  **silently**. scripts/install.sh copies the file, so the documented install is not affected. Suggest a
  warning when `~/.local/bin/ccwm` is a symlink.
- **I3. Cost of a large prompt (E4).** A 16 MiB `UserPromptSubmit` input takes 0.19 s with the release build
  and 0.8 s with the debug build (the watchdog ends the hook at 1 s, so a debug build loses such events
  under load). `read_input` feeds `serde_json::from_reader` byte by byte from the stdin buffer; fine for
  release, worth knowing for manual tests with a debug build.
- **I4. A test that hangs instead of failing.** Under mutation C1 (no `SO_SNDTIMEO`),
  `client::tests::a_full_listen_queue_costs_the_budget_and_no_more` (`src/client.rs:282`) blocks forever in
  `connect()`; I stopped it after 150 s. It does catch the regression, but as a CI timeout. Running the call
  on a thread and failing after, say, 2 s would make it a failure.
- **I5. Two mutations survive by design.** L3: the terminal hint (`if stdin.is_terminal()`,
  `src/cli.rs:228`) is untested — cosmetic. I2: logging the request's `Debug` at trace instead of its name
  is not caught, because `Report`'s `Debug` hides the cwd; with both layers removed (I2+H9) the trace-log
  check of `a_fake_claude_tree_reports_through_the_printed_hooks` fails. Two layers, verified together.
- **I6. DRY.** The "refused: …" text is built by two identical closures in `format_hook_events_header`
  (`src/cli.rs:325`) and `format_hooks` (`:637`); `doctor::hooks` hard-codes the four refusal names
  (`src/doctor.rs:137`) instead of using `Refusal::ALL`, so a fifth reason would be missed there; and
  `Refused::slot`/`Refused::get` (`src/presence/store.rs:270-286`) repeat the same mapping.
- **I7. `hooks events --follow` across a restart.** The loop's `client::call(…)?` (`src/cli.rs:299`) ends
  the command on the first failed poll, so "-- the daemon restarted --" appears only when a restart falls
  between two polls 300 ms apart; a normal `ccwm restart` ends `--follow` with an error. Retrying while the
  instance lock is held (as `first_call` does) would match the documented behaviour.
- **I8. Hidden sessions count against the limit.** Non-interactive sessions are hidden by default but count
  toward the 256 sessions (`MAX_SESSIONS`); a large parallel `-p` fan-out makes the next interactive
  session's events be refused `limit`. Probably acceptable; worth a line in docs/session-hooks.md.
- **I9. Documentation drift.** `CLAUDE.md` says v0.1.1 is "built, not tagged", but the repository has an
  annotated tag `v0.1.1` at `972f083` (the base of this review). SECURITY.md's "deleted when the session closes" is
  best effort (the writer drops the delete when its queue is full, and L2's ghost keeps the row).

## Reviewed and found sound

From the code, except where a mutation or an experiment above covers the point.

- **Socket message.** `parse_request` sends `hook.event` to `Report::from_request`, which checks the exact
  key set per event (`source` only and required for `SessionStart`, `notification_type` only and required
  for `Notification`), lower-case UUIDs, the cwd shape (absolute, ≤ 4,096 bytes, no NUL), and `claude_pid`
  as an integer in 2…4,194,304 (floats, strings and negatives refused). Every other op still needs exactly
  one key. A malformed event is answered and counted, logging only a known event name and a valid session
  id. 32 KiB covers a 4,096-byte cwd escaped as `\u00XX` throughout (tested). The server reads at most
  32 KiB + 1 per connection and logs op names only.
- **The hook's stdin.** Allowlist with `IgnoredAny`/lenient strings; the object-only wrapper refuses arrays;
  parsing stops after the first value (an open stdin holds nothing up); `take(16 MiB)`. Canaries in every
  skipped field of every fixture are checked against the socket request, the trace log, the database and
  the debug log.
- **Exit status and stdout.** `main` dispatches `hook` before clap (no usage error, no status 2); the panic
  hook prints one stderr line and exits 0; every path ends in `process::exit(0)`; nothing uses stdout. The
  watchdog thread is started before stdin is read. With the guard, even an abort or a signal ends in
  status 0 from the shell.
- **The budget.** One deadline covers connect (`SO_SNDTIMEO`, so a full listen queue cannot block),
  `SO_PEERCRED` check of the daemon's UID, write and read; no retry, no wait for a starting daemon; the
  answer is bounded to 4 KiB. A missing socket returns at once.
- **The walk.** Real and effective UID must be the daemon's at every step (the walk stops at the first
  other user, so another user's `claude` above a foreign process is never reached); a parent that started
  after its child stops it; pid 1 and 8 steps bound it; `stat` is parsed after the last `)`; `cmdline` is
  bounded, split on NUL, and dropped after the `argv[0]` and option checks; zombies count as gone. Another
  user cannot connect at all (peer UID check), so cross-user spoofing is limited to being an ancestor,
  which the UID rule excludes. Same-user spoofing is out of scope and documented as such (SECURITY.md).
- **Identity and restart.** (pid, start time, boot id); restore re-reads UID, `argv[0]` and the interactive
  flag, puts sessions in `unknown` without a prompt id, and deletes what it drops; the boot id read once.
- **State machine.** The table of §21.6 is implemented as written and tested event × state; `compact`
  keeps state and prompt id; `UserPromptSubmit` and `SessionStart` are never stale; an unknown prompt id is
  learned from the next event; facts apply by prompt id, else by record time against the state's entry
  time, so a file read again from byte 0 changes nothing. Persistence writes are best effort and never
  awaited by the hook's answer.
- **Privacy.** `LiveView` and `SessionLive` hold states, counts and times; the project and session
  payloads are the same in privacy mode; the debug log holds names, times, session ids and outcomes and is
  reachable over the Unix socket only; `/service/status` carries counts and reason names. `Report` and
  `Open` have a `Debug` without the cwd.
- **Sandbox.** The daemon opens no socket for any of this and starts no process; only `ccwm hook`, a
  client process outside the daemon, creates a socket.
- **UI.** No `innerHTML`; the dot is `aria-hidden`, the label is text, the details are in `title` and a
  screen-reader span; reduced motion stops the pulse; the minute counter is refreshed from a data attribute.

## Appendix: how the experiments were run

All in a clone of `72b1a70` under the session's temporary folder; scratch code was reverted after each run.

- **E1, E2 (store).** A scratch `#[cfg(test)]` module appended to `src/presence/store.rs` in the clone:
  E1 applies `SessionStart` (pid 10), `SessionStart(resume)` (pid 20), `UserPromptSubmit` (pid 20, prompt

  `SessionStart` X (pid 10) and `SessionStart(clear)` Y (pid 10) without X's `SessionEnd`, assigns both to
  one project and asserts an aggregate of 2 sessions and 2 tracked identities (passes).
