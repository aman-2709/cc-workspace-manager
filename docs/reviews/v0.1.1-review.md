## Medium

### M1. Walks of new directories compile ignore rules outside the limit across projects

**Where.** `src/watch/mod.rs:1082-1120` (`walk_new_dir`: the allowance at `:1101`, one
`spawn_blocking` per created directory at `:1102`, called from `:1025`), `src/watch/mod.rs:723-735`
(`watch_new_tree` uses only the directories of the result), `src/watch/tree.rs:387-389` (`room`).

**What happens.** Every directory that is created in, or moved into, a watched project is walked at
once on a blocking thread of its own. The walk loads the `.gitignore` files it finds, with an
allowance of `room(root)`: what the store would let the project hold. `room` reserves nothing, and
the rules such a walk compiles are dropped when it ends, so the store never counts them. N
directories that appear together are N walks, and each may compile up to the project limit (5,000
rules) at the same time. The only bound is Tokio's blocking pool (512 threads).

**Demonstrated.** Unmodified release builds of `597bb74` in a synthetic environment; one watched
project with a `.git`; directories that each hold a `.gitignore` of 4,900 rules of the benchmark's
shape (`*1?b[c-d]*.x`), prepared in a hidden folder and moved into the project together.

| Directories | Build | RSS before | Peak RSS | RSS 30 s later |
|---|---|---|---|---|
| 1 | glibc | 14 MiB | 96 MiB | 96 MiB |
| 24 | glibc | 14 MiB | **2,137 MiB** | 1,740 MiB |
| 24 | musl (the release target) | 11 MiB | **2,462 MiB** | 21 MiB |

That is 80–100 MiB per directory. `ccwm status` reported no skipped file afterwards: the store does
not see these rules. The unit's limit of 2 GiB is passed at about two dozen directories (the daemon
was started by hand here, not under the unit).

**Impact.** Availability. Under the unit the kernel would kill the service at that peak and systemd
would restart it (not run under the unit). After a restart the tree is walked by the tracker, one
project at a time and within the limits, so I expect one cycle and not a loop. A daemon started by
hand has no bound. The trigger is a hostile tree unpacked or checked out inside a watched
project. A `git clone` qualifies: the project is registered when its `.git` or its marker appears,
and the rest of the checkout arrives as new directories.

The documents state a bound that does not hold: `SECURITY.md` "Ignore rules cost memory" ("345–395
MiB for all", "at most one project's worth at a time"), `docs/service.md:131` and
`src/systemd.rs:20-25` ("the worst case its ignore-rule limits allow was measured at 395 MiB").

**Relation to v0.1.0.** The concurrent walks are older than v0.1.1: the per-project limit of the fix
pass was per walk as well. v0.1.1 put `room()` in front of these walks and wrote the bound into the
documents, so the finding belongs here. Mutation M18 replaces both `room()` calls with the constant
and no test fails: the limit in subtree walks is untested.

**A side effect of the same code, also older than v0.1.1 (reasoned).** Because the result's rules
are dropped, a `.gitignore` inside a directory created at runtime does not apply to later events in
that directory until the project's next full walk.

**Fix.** Do not compile in these walks. Give `walk_new_dir` an allowance equal to the rules the
project already holds (`state.ignore.patterns()`), so it only reuses. When the walk met an ignore
file it could not take (`tree.ignore_files_skipped > 0`), set `rewalk` for the project: the tracker's
full walk goes through `begin`/`settle`, one signal at a time, loads the new files within both limits,
and removes the side effect too. A smaller change is to run new-directory walks through one worker,
so that one compiles at a time; that leaves the side effect. Either way, add a daemon-level test in
the style of `repeated_scans_…` (N directories appear, the peak stays within one project's worth)
and correct the three documents.

### M2. A project without watches that lacks its rules never shows new activity

**Where.** `src/tracker/mod.rs:722-733` (`record_inferred`), reached from `refresh_polled`
(`:556-558` and `:571-572`).

**What happens.** The rule approved on 2026-11-26 says: a scan of a project that lacks its rules does
not move a known time; what the watcher observes does, and that "is what brings its rules back". A
polled project has no watcher. Scans are its only source of activity, so once it is without rules:

1. no change in it is recorded any more;
2. its place in the order by recency therefore never improves;
3. so it never gets its rules back.

The state ends only when more recent projects leave or the project gets watches. Both budgets, the
watches (§5.1) and the rules (§5.2), go to the most recently active projects, so the least recent
projects are the ones that lose both. Where no inotify instance is available every project is polled
(`CLAUDE.md` records about 109 of this host's 128 instances in use by other programs).

**Demonstrated.** A scratch test through the real tracker and monitor (appendix): two projects of
four rules each and a watch budget of one, so the more recent project gets the watch and `a-older`
is `Polled`. A file that no rule names is written into `a-older` with a modification time 10 s ago,
then three scans run.

| Rules all projects may keep | Rules kept (older, newer) | Recorded activity of `a-older` after the scans |
|---|---|---|
| 8 (control) | 4, 4 | `notes.txt`, inferred, 10 s old |
| 4 | 0, 4 | unchanged: `.gitignore`, 3,000 s old |

**Impact.** A stale "last change" and activity status are shown as fact, with no sign that the
project is held back. The advice in `ccwm status` says the opposite for these projects ("files they
would ignore count as activity", `src/watch/mod.rs:1233`). The consequence is not in REQUIREMENTS
§5.2, ARCHITECTURE §7a, the CHANGELOG or SECURITY.md, so the approval did not cover it. It needs more
than 20,000 rule lines over all projects (I4 on how ordinary that is) and projects without watches.

**Fix: two options.**

1. *Scan a project that lacks rules with its rules, and do not keep them.* When a full walk comes
   back with files left out for the allowance alone (`ignore_rules_wanted` above what it kept), walk
   again with the project limit, take only `newest` from that walk and drop its rules. `walk_many` is
   sequential, so one project's worth is compiled at a time. Scans are then right for every project,
   the special case in `record_inferred` is no longer needed, and no walk without rules feeds the
   order. The cost: such a project's rules are compiled at every scan that walks it (up to 1.2 s for
   5,000 expensive rules), and a glibc build may keep the freed memory, which is the effect the cache
   removed.
2. *Keep the rule and say so.* Document the consequence, count such projects in the monitoring
   status, replace the advice sentence, and mark the project's card.

I recommend option 2 for v0.1.1, because the consequence needs the maintainer's decision, and option
1 afterwards.

## Low

### L1. Two full walks of one project at once release its reservation early

**Where.** `src/watch/tree.rs:394-430` (`reserved` is overwritten at `:405` and taken by the first
`settle` at `:421`), `:484` (`contended`, the gate of `rebalance_rules`).

**What happens.** Full walks start in three places that are not serialized: the reconciler task
(`reconcile`, `refresh_polled`, `rebalance_rules` at `src/tracker/mod.rs:299`), the signals task
(`enroll` for `Rewalk`, `Discover` and `Sessions`, and `rebalance_rules` at `:914-916`), and control
calls (`:857`). `rebalance_rules` runs in both tasks, from the same plan. When two walks of one root
overlap, the second `begin` overwrites the reservation and the first `settle` clears it while the
second walk still runs. Another project's `begin` then gets that room, and the second `settle`
stores more than the store thinks is left.

**Demonstrated at the store** (unit test in the appendix): limit 10, `total()` is 18. No project
lacks rules, so `contended()` is false and `rebalance_rules` returns at once; `rebalance()` would
name the correcting walk but is never asked. The overlap in the tracker is reasoned.

**Fix.** Keep the reservation until the last walk of that root settles (count the walks in progress
and keep the largest allowance), or allow one full walk per root at a time. Also let
`rebalance_rules` run when `total()` is above the limit, not only when a project lacks rules.

### L2. `retain` with an old project list drops projects enrolled since

**Where.** `src/tracker/mod.rs:643-654`, called by `walk_context` (`:655`) with a `tracked` list
that was read earlier: once per walk inside the loop of `rebalance_rules` (list at `:684`, call at
`:697`), and in `refresh_polled` for the subtree walks (`:571`) after the whole walks (`:554`) with
the list from `:534`.

**What happens (reasoned).** A project that the signals task enrolls during one of those walks is
in the store but not in the reconciler's list, and the next `walk_context` drops it. Its rules stay
in the monitor. The store no longer counts them, so other projects can take their room (up to 5,000
rules over the limit per such project), and `rebalance` and `lacks_rules` do not see the project
until its next full walk. For a fully watched project that is the next `.gitignore` change, an
overflow or a restart.

Mutation M19 removes the `retain` call altogether and no test above the store's unit test fails:
that a project which leaves frees its share is untested in the tracker.

**Fix.** Remove a project from the store where it leaves monitoring (`unwatch`, missing, ignored),
not by list; or call `retain` only with a list read immediately before. Never drop an entry that
has a reservation.

### L3. A blocked WAL truncation makes every write batch wait; the debt is forgotten at a restart

**Where.** `src/db/writer.rs:581-597` (`truncate_wal`), `:626-628` (the retry), `:547` (the flag).

**What happens (reasoned).** The fix itself is right (table below). Two things around it:

- While a reader keeps blocking, every later batch runs the checkpoint again with the connection's
  `busy_timeout` of 5 s (`src/db/mod.rs:78`), before that batch's replies are sent, and logs the
  warning again. The writer then completes one batch per 5 s and every caller that waits for a write
  waits with it. The unit test lowers the timeout to 50 ms for this reason (`:1428`). ccwm's own
  readers are short, so this needs another process that holds a read transaction on `ccwm.db`, such
  as a `sqlite3` shell.
- `truncation_owed` lives in memory. A daemon that stops while it owes a truncation leaves the frames
  in the file, and the next start does not know.

**Fix.** Retry with a timeout of zero (`conn.busy_timeout(Duration::ZERO)` around the retries; the
first attempt keeps 5 s). Warn once when the debt arises and log once when it is paid. Start with
`truncation_owed = true`: one cheap checkpoint at the first batch pays whatever an earlier run left.

### L4. Unit: a child that reaches the limit stops the daemon; the restart loop has no end

**Where.** `src/systemd.rs:46-56`.

**(a) Demonstrated.** `MemoryMax=` covers the daemon and its children together, and this user
manager's `DefaultOOMPolicy` is `stop`: when the kernel kills any process of the unit, systemd stops
the whole unit, and `Restart=on-failure` starts it again. So a `git status` or `claude --version`
that reaches the limit takes the daemon with it, although ccwm already treats a failed Git command
as a status. Two transient user units (`MemoryMax=64M`, `MemorySwapMax=0`, a shell whose child
allocates 300 MiB) showed it: with the default the shell was stopped together with the child; with
`OOMPolicy=continue` the child was killed (status 137) and the shell went on. Consider
`OOMPolicy=continue`, verified with the real daemon like the other directives (ARCHITECTURE.md §13).
When the daemon itself is the largest process, the kernel picks it and the service restarts as now.

**(b) Reasoned.** With `RestartSec=5` the default start limit (5 starts in 10 s) cannot be reached,
so a persistent cause restarts the service for ever; SECURITY.md says so ("for as long as the cause
is there"). `StartLimitIntervalSec=` and `StartLimitBurst=` in `[Unit]` (for example 5 starts in 10
minutes) would end the loop in a failed state that `ccwm status` and `ccwm doctor` show. A design
choice, not a defect.

### L5. Shutdown can start one more reconciliation; an acceptance test fails now and then

**Where.** `src/daemon.rs:461-462`, `src/tracker/mod.rs:188-191` (`cancel`), the test at
`tests/process.rs:1891-1911`. This code is older than v0.1.1 and not in the diff.

**What happens.** `tracker.cancel()` wakes the reconciler through `refresh.notify_one()` *before*
`stop_tx.send(true)`. When the reconciler task runs between the two statements it sees no stop and
starts a reconciliation: it ingests and stores the sessions, and only then finds the scan cancelled.
The acceptance test clears the session index and stops the daemon; the ingest during shutdown
indexes the sessions again, and the test finds a session title in the database files.

**Demonstrated.** The full `tests/process.rs` 40 times at `597bb74`: 4 failures, three of them
while a release build ran alongside and one without other load. In a failing run the title is in
`ccwm.db-wal` (11 frames) and not in `ccwm.db`, there is no WAL warning, and no "reconciliation
finished" follows the clear. With a 100 ms sleep between the two statements the test fails 3 times
of 3 with the same signature.

**Why it matters now.** Any CI run can hit this, and the failure reads like a failure of the WAL
truncation (I7), which it is not. In the product, "Clear session
index" followed by a stop rebuilds the index during shutdown.

**Fix.** Send the stop first (swap the two statements), or drop the notify from `cancel()`
(`until_stopped` already ends the reconciler's sleep), or check `cancel` at the top of the loop.

### L6. Allocation by recency: three statements in the documents do not match the code

1. *"That activity is what brings its rules back"* (REQUIREMENTS.md:110, ARCHITECTURE.md §7a,
   `src/tracker/mod.rs:719-721`) reads as if it were real activity. The watcher cannot tell an
   ignored file from a meaningful one in a project without rules either. The repository's own test
   shows it: `a-oldest` gets its rules back through `one.tmp`, a file its rules name
   (`tests/tracker.rs:662-692`). A watched project without rules that writes ignored files therefore
   gets one wrong observed activity each time it loses its rules, and takes the rules of the least
   recent holder. This does not loop tightly: once it holds its rules, its ignored files stop
   counting.
2. *A project's first walk under contention* records a time that may come from an ignored file ("it
   needs a place in the order"). `record_activity` only moves a time forward
   (`src/db/writer.rs:1140-1148`), so the later walk with rules never corrects it (reasoned). Option 1
   of M2 removes this case.
3. *"At the next scan"* (CHANGELOG, `src/tracker/mod.rs:861-863`): the rules follow a changed order
   after every signal that is not `Activity`, `Git` or `Rescan` (`:864-867`, `:914-916`), and
   `Signal::Sessions` arrives whenever a session file changes. The rules can therefore move far more
   often than once per scan.

**Fix.** Wording for 1 and 3; nothing more is needed for v0.1.1.

## Info

- **I1. The error text of `settable_path` promises more than it checks.** It says "without `.` or
  `..`" (`src/service.rs:1166-1178`), but `Path::components()` drops `.`, and the test accepts
  `/home/u/./dev` on purpose (`tests/sessions_api.rs:1208`). Either reject `.` by looking at the
  string, or drop it from the message and the doc comment.
- **I2. A listing cut off at the limit keeps everything, for ever.** Correct and conservative, but a
  session deleted on disk then stays in the index as long as more than 100,000 files exist. The
  directories listed before the limit was reached are complete; marking those would let their
  sessions be removed. The warning (`src/tracker/sessions.rs:68-73`) is logged at every ingest, that
  is at every session change, and the state is not in `ccwm status`.
- **I3. Rules of a repository above several projects are compiled and counted once per project.**
  The cache is per project root (`src/watch/tree.rs:723-751` loads the layers for each project). A
  repository with 50 marker directories and a 200-line root `.gitignore` takes 10,000 of the 20,000
  rules (reasoned). Sharing those layers, or counting them once, would fit the limit's purpose.
- **I4. The limit counts rule lines whatever they cost.** Ordinary rules cost almost nothing
  (SECURITY.md), yet they count like expensive ones. An estimate, not a measurement: with about 100
  rule lines in a `.gitignore` from a common template, some 200 repositories reach 20,000, and the
  least recent projects then lose their rules with memory nowhere near a limit. Worth weighing when
  `MemoryMax=` is tightened (ROADMAP.md "After v0.1.1"): count, or weigh more, only the rules that
  need a regular expression.
- **I5. The cache's blind spot is the file system's timestamp step, not always milliseconds.** The
  key and the order of operations are right (identity is taken before the read, so a write during
  the read is seen next time). The documented residual (a same-size rewrite within one timestamp
  step of the previous change, after a walk read the file within that step) is given as
  "milliseconds on ext4"; the step is coarser on some file systems, for example 1 s on ext4 with
  128-byte inodes and 2 s for FAT's modification time (reasoned, not run on one). Git's rule for the
  same problem would close it: do not reuse a layer whose file changed less than two seconds before
  it was read; it is compiled once more at the next walk.
- **I6. `a_directory_on_another_file_system_is_not_entered` writes to `/dev/shm`**
  (`tests/discovery.rs:687`). A good test with both controls, but `CLAUDE.md`'s hard rule allows
  writes only in the repository, cargo's cache and `/tmp`. Amend the rule or note the exception.
- **I7. `purge_is_refused_while_a_daemon_outside_systemd_holds_the_lock` leaves its daemon running
  when it fails** (`tests/service.rs:531`, spawned at `:538` without a guard). Mutation M23 left a
  `ccwm serve` running for 14 minutes on a deleted synthetic home. Each such daemon holds an inotify
  instance, which is scarce on this host. Kill it in a drop guard.

## Reviewed and found sound

By reading the code, except where a mutation above covers the point.

- **`PUT /settings` (I6).** Roots and the session directory are judged after symlinks are resolved,
  against the canonical home (`src/daemon.rs:115`); a list given as a string or with entries that are
  not strings fails in deserialization; duplicate keys reach the check and the merge as the same
  value; `//`, a trailing slash and `/proc/self/root` resolve to what they are. A path that does not
  exist is judged by its spelling, which cannot name an ancestor of home without being one.
- **WebSocket (I3).** A revocation and the periodic check come before a client message and before an
  event; a blocked send ends the session after 5 s, the close frame included; an event that arrived
  after the revocation is never sent.
- **WAL truncation (I7).** The result row is read, a blocked truncation is reported and owed across
  batches, and an ordinary batch leaves the log alone.
- **Session listing (I8).** `truncated` is set for the whole listing and for partial ones, and
  `gone_files` removes nothing from such a listing in either mode.
- **Rule cache.** The key is the location (directory, and whether it is `info/exclude`) plus device,
  inode, size, modification time and change time, read from the open file before its content. Hard
  links keep rules of their own per directory. A full walk carries over only what it found again, so
  rules of deleted files go with the old set; a project that leaves, wants no rules or fails its walk
  is dropped. Reused layers pass the same limits as fresh ones.
- **Allocation.** The shares are a function of the projects alone; giving up comes before taking;
  `walked_with` stops a project whose file cannot fit from being walked again and again.
